Azure ורשתות הענן

// 01 — ממש מהיסוד

מה זה בכלל "ענן"?

לפני ש-Azure יעזור לנו — צריך להבין מה זה מחשוב ענן בכלל, בלי מונחים מפחידים.

🖥️ נתחיל מהבסיס — מה זה שרת?

שרת (Server) הוא בפשטות מחשב חזק שנשאר דלוק כל הזמן ומספק שירות למחשבים אחרים — למשל, מחשב ששומר אתר אינטרנט, או מחשב ששומר את המסמכים של החברה.


בעבר, כל חברה קנתה שרתים משלה, שמה אותם בחדר מיוחד (Data Center פרטי) ותחזקה אותם בעצמה. זה נקרא On-Premises (On-Prem) — "אצלנו בבית".

☁️ אז מה זה "ענן"?

"ענן" הוא לא באמת ענן באוויר — זה פשוט המחשב של מישהו אחר, שיושב במרכז נתונים ענק (Data Center) שבבעלות חברה כמו Microsoft, Amazon או Google, ומחובר לאינטרנט.


במקום לקנות שרת ולתחזק אותו בעצמך, אתה שוכר חלקיק ממחשב ענק כזה, דרך האינטרנט, ומשלם רק על מה שאתה באמת משתמש בו — בדיוק כמו חשבון חשמל.

🏠 אנלוגיה: לקנות בית מול לשכור דירה

On-Premises (לקנות בית)ענן / Azure (לשכור דירה)

אם צריך יותר מקום — צריך לבנות/לקנות עודלוחצים כפתור ומקבלים עוד "מקום" תוך דקות
שדרוג לוקח שבועות/חודשיםשינוי גודל תוך שניות (Scale up/down)

🍕 IaaS / PaaS / SaaS — אנלוגיית הפיצה

מודלמה מקבליםאנלוגיה (פיצה)

Azure מציע את כל השלושה — ואנחנו נתמקד בעיקר ב-IaaS, כי שם חיה כל הרשת.

🌍 מה זה בדיוק Microsoft Azure?

Azure הוא פלטפורמת הענן הציבורי של Microsoft — מאות מרכזי נתונים ברחבי העולם, המחוברים ביניהם ברשת פרטית ענקית של מיקרוסופט, ומציעים אלפי שירותים: שרתים וירטואליים, מסדי נתונים, אחסון, בינה מלאכותית — וכמובן, רשתות, שבהן נתמקד במדריך הזה.


המתחרות העיקריות: AWS (אמזון) ו-Google Cloud (GCP). כולן עובדות על אותו רעיון בסיסי.

💡 למה זה חשוב להבין את הרשת דווקא?

אפשר לחשוב על Azure כמו עיר ענקית: יש בה בניינים (שרתים ושירותים), אבל בלי כבישים, כתובות ושילוט — אף אחד לא יכול להגיע לאף מקום. הרשת ב-Azure היא בדיוק זה: הכבישים, הגבולות, השערים והמאבטחים שקובעים מי יכול לדבר עם מי, מאיפה ולאן. זה הבסיס לכל דבר אחר שתבנו בענן.

// 02 — ארגון וניהול

איך Azure מאורגן?

לפני שנכנסים לרשתות — צריך להבין את "התיקיות" שבתוכן הכל נשמר.

🏢 Management Group (קבוצת ניהול) — "כל הארגון"
💳 Subscription (מנוי) — "כרטיס האשראי / יחידת חיוב"
📁 Resource Group (קבוצת משאבים) — "תיקייה"
🖥️ Resource (משאב) — VNet, VM, Storage Account...
🌐 Resource — עוד VNet, NSG...

📁 Resource Group — "תיקייה" למשאבים

Resource Group (RG) הוא פשוט תיקייה לוגית שבה שמים משאבים ששייכים יחד — למשל, כל מה שקשור לאתר אחד: השרת, הרשת, מסד הנתונים. מוחקים את ה-RG — מוחקים הכל שבתוכו.

💳 Subscription — יחידת חיוב וגבול הרשאות

Subscription קובע מי משלם ומהו התקציב/המכסה. זה גם גבול אבטחה חשוב — לכל Subscription יש הרשאות (RBAC) נפרדות. ארגון יכול להחזיק כמה מנויים (למשל: פיתוח, בדיקות, ייצור).

🌍 Region — איפה פיזית יושב המשאב

Region הוא אזור גיאוגרפי שבו יש מרכזי נתונים של מיקרוסופט — לדוגמה West Europe (הולנד) או East US. כשיוצרים משאב, בוחרים באיזה Region הוא יחיה. חשוב: משאבי רשת (כמו VNet) שייכים ל-Region אחד בלבד.

🏗️ Availability Zone — הגנה מתקלות

בתוך רוב ה-Regions הגדולים יש כמה Availability Zones — מרכזי נתונים נפרדים פיזית עם חשמל, קירור וחיבור אינטרנט משלהם. פורסים משאבים על פני כמה Zones כדי שאם אחד נופל, השירות ממשיך לרוץ.

🔗 Region Pair — "זוג גיבוי" גיאוגרפי

לרוב ה-Regions יש "אח תאום" רחוק ממנו מספיק (בדרך כלל באותה מדינה/יבשת), המיועד לגיבוי ואסון — למשל West Europe (הולנד) מזווג עם North Europe (אירלנד). זה שימושי לתכנון Disaster Recovery.

# יצירת Resource Group חדש דרך Azure CLI:
az group create --name MyRG --location westeurope

# הצגת כל ה-Subscriptions הזמינים:
az account list --output table
// 03 — הכלים לניהול

איך מנהלים את כל זה?

ארבע דרכים שונות "לדבר" עם Azure, ושתי שכבות ממשל ששומרות על סדר כשהארגון גדל.

🖱️ Azure Portal

ממשק האינטרנט הגרפי הרשמי לניהול Azure — לוחות בקרה (Dashboards), אשפים ליצירת משאבים, גרפים לניטור וניהול משתמשים. הכי נוח למי שרק מתחיל או לבדיקה חד-פעמית, אבל לא מתאים לפעולות חוזרות בקנה מידה גדול.

⌨️ Azure CLI ו-Azure PowerShell

שתי דרכים "לתכנת" את הניהול מתוך טרמינל: Azure CLI (פקודות בסגנון az ..., חוצה מערכות הפעלה) ו-Azure PowerShell (מודול Az, מתאים למי שכבר מכיר PowerShell). שניהם מאפשרים לכתוב סקריפטים ולחזור על אותה פעולה במדויק פעמים רבות — בדיוק כמו הפקודות שראיתם כבר בכל המדריך הזה.

⚙️ Azure Resource Manager (ARM) — המנוע שמאחורי הכל

בין אם משתמשים בפורטל, ב-CLI או ב-PowerShell — כולם בסוף פונים לאותה שכבה: ARM. זהו המנוע שמקבל בקשה ("תיצור לי VNet כזה") ומבצע אותה בפועל. אפשר גם לכתוב את כל התצורה הרצויה מראש בקובץ (ARM Template בפורמט JSON, או Bicep — שפה נוחה יותר שמתורגמת ל-ARM) ולהריץ אותו — גישה שנקראת Infrastructure as Code (IaC): הרשת והמשאבים שלכם מתועדים כקוד, ניתנים לשחזור ולביקורת בדיוק כמו כל קוד אחר.

📜 Azure Policy — שומר הסדר הארגוני

מנגנון שאוכף חוקים על כל מה שנוצר ב-Subscription — למשל: "אסור ליצור משאבים מחוץ ל-Israel Central", "כל VM חייב תגית Owner", או "אסור ליצור Public IP מסוג Basic". פוליסה יכולה רק להתריע (Audit) או גם לחסום יצירה בפועל (Deny) — כלי הממשל (Governance) המרכזי של Azure.

🏢 Tenant מול Subscription — לא לבלבל!

Tenant הוא גבול הזהות של הארגון — ספרייה יחידה ב-Microsoft Entra ID שמכילה את כל המשתמשים וההרשאות שלכם. Subscription הוא גבול החיוב וההרשאות למשאבים, וחי בתוך Tenant אחד. ארגון אחד = בדרך כלל Tenant אחד, אך יכול להכיל בתוכו הרבה Subscriptions (לפי מחלקות, סביבות וכו').

📦 Azure Blueprints — היה, ולאן זה עבר

בעבר, Azure Blueprints שימש לארוז יחד תבניות ARM, פוליסות והרשאות לפריסה אחידה של סביבות תואמות-רגולציה. מיקרוסופט הוציאה את השירות משימוש (Retired), וכיום הדרך המומלצת היא שילוב של Template Specs ו-Deployment Stacks יחד עם Azure Policy — שווה לדעת את השם הישן אם נתקלים בו בתיעוד או בסביבות ותיקות.

// 04 — מי אתה ומה מותר לך

אבטחה וניהול זהויות

מי מורשה להיכנס, מאיפה, ומה קורה אם משהו חשוד קורה.

🪪 Microsoft Entra ID (לשעבר Azure AD)

שירות ניהול הזהויות המרכזי של Azure — הוא ה"ספר הטלפונים" שיודע מי המשתמשים, הקבוצות והאפליקציות בארגון, ומה מותר לכל אחד מהם. הוא זה שמאמת אתכם כשאתם נכנסים לפורטל, ומה שמאפשר Single Sign-On (SSO) ו-MFA (אימות דו-שלבי) בכל שירותי מיקרוסופט וגם באפליקציות חיצוניות. (השם שונה מ-"Azure Active Directory" ל-Microsoft Entra ID — אותו שירות, שם חדש.)

🚦 Conditional Access

מנגנון חוקים שמחליט בזמן אמת אם להתיר כניסה — לא רק לפי סיסמה נכונה, אלא גם לפי מאיפה מתחברים (מדינה), מאיזה מכשיר (מנוהל/לא מנוהל), ורמת סיכון ההתחברות. לדוגמה: "דרוש MFA אם ההתחברות מגיעה ממדינה לא מוכרת", או "חסום גישה ממכשירים שלא עומדים במדיניות הארגון".

🌍 Microsoft Entra External ID (לשעבר Azure AD B2C)

בעוד Entra ID "הרגיל" מנהל עובדים פנימיים, External ID מנהל זהויות של לקוחות חיצוניים — למשל משתמשים שנרשמים לאפליקציית מובייל או לאתר מסחר. מאפשר התחברות עם Google, Facebook או אימייל רגיל, בלי לתת להם גישה לשום דבר פנימי בארגון.

🔗 Microsoft Entra Domain Services (AAD DS)

שירות מנוהל שנותן יכולות בסגנון Active Directory מוכר — Kerberos, NTLM, LDAP ומדיניות דמויות GPO — בלי להקים ולתחזק Domain Controllers בעצמכם. שימושי בעיקר להעברת אפליקציות ותיקות (Legacy) לענן מבלי לשכתב אותן מחדש, ובתרחישים היברידיים יחד עם ה-AD המקומי (On-Prem) שלכם.

🛡️ Microsoft Defender for Cloud

פלטפורמת אבטחה שסורקת את כל הסביבה (וגם היברידית/רב-ענן) ונותנת Secure Score — ציון המשקף כמה אתם חשופים, עם המלצות קונקרטיות לתיקון. כוללת גם הגנת זמן-ריצה (Workload Protection) על VMs, מאגרי מידע ומכולות.

🔑 Azure Key Vault

כספת דיגיטלית מרכזית לאחסון סודות, מפתחות הצפנה ותעודות (Certificates) — כדי שאפליקציות לא ישמרו סיסמאות או API Keys בקוד המקור. גישה נשלטת בהרשאות מדויקות, וכל שימוש נרשם ביומן ביקורת.

🕵️ Microsoft Sentinel — ה"חדר בקרה" הביטחוני

SIEM/SOAR מבוסס ענן — אוסף לוגים והתראות מכל הסביבה (Azure, On-Prem, ואפילו עננים אחרים), מזהה דפוסי התקפה חשודים באמצעות ניתוח וכללים חכמים, ויכול אף להפעיל תגובה אוטומטית (למשל: לנתק אוטומטית משתמש שנחשד בפריצה). זהו הכלי שרואה את "התמונה המלאה" מכל שאר כלי האבטחה יחד.

💡 איך כל זה מתחבר יחד

Entra ID קובע מי אתם. Conditional Access קובע באילו תנאים מותר לכם להיכנס. Key Vault שומר את הסודות שהאפליקציות שלכם צריכות. Defender for Cloud בודק שההגדרות שלכם תקינות. Sentinel צופה על הכל ומתריע אם משהו חורג. זו הגנה בשכבות (Defense in Depth).

// 05 — היכן הקוד באמת רץ

מחשוב ב-Azure — Compute

מ"שרת וירטואלי רגיל" ועד קוד שרץ לשניות בודדות בלי שרת בכלל.

🖥️

Azure Virtual Machines

שרת וירטואלי מלא (IaaS) — שליטה מוחלטת על מערכת ההפעלה, בדיוק כמו שרת פיזי, רק בענן.

📈

Virtual Machine Scale Sets

קבוצת VMs זהים שגדלה ומצטמצמת אוטומטית לפי עומס (Auto Scaling) — בסיס לאתרים גדולים.

☸️

Azure Kubernetes Service (AKS)

Kubernetes מנוהל — מריץ אפליקציות ארוזות במכולות (Containers) בקנה מידה, בלי לנהל את השרתים בעצמכם.

🌐

Azure App Service

PaaS להרצת אתרים ו-APIs (.NET, Node.js, Python, Java...) — מעלים קוד, Azure מטפל בשרת, בגיבוי ובקנה המידה.

⚡

Azure Functions

קוד "חסר שרת" (Serverless) שרץ רק כשמפעילים אותו (למשל בקשת HTTP או קובץ חדש) — משלמים רק על זמן ריצה בפועל.

🔀

Azure Logic Apps

בניית תהליכים אוטומטיים בגרירה-והשלכה בין עשרות שירותים, כמעט בלי לכתוב קוד בכלל.

🧮

Azure Batch

הרצת עבודות חישוב מקבילות בקנה מידה ענק (HPC) — למשל עיבוד וידאו או סימולציות מדעיות על אלפי ליבות בו-זמנית.

🍕 חזרה לאנלוגיית הפיצה — איפה כל שירות נמצא

Virtual Machines = IaaS (אתם אחראים כמעט על הכל). App Service ו-AKS = PaaS (הפלטפורמה מוכנה, אתם רק מריצים עליה). Azure Functions ו-Logic Apps = Serverless (הקצה הכי "משוחרר" — אין בכלל שרת לחשוב עליו, רק הקוד/התהליך עצמו).

// 06 — איפה המידע נשמר

אחסון ומסדי נתונים

מקבצים גולמיים ועד מסדי נתונים גלובליים בקנה מידה ענק.

🗄️

Azure Storage Account

ה"מיכל" העל שמאחד תחתיו את שירותי האחסון: Blob, Files, Queues ו-Tables. כל דבר שנשמר ב-Azure שאינו מסד נתונים מובנה — עובר דרכו.

📦

Azure Blob Storage

אחסון לקבצים לא-מובְנים בכמויות עצומות — תמונות, וידאו, גיבויים, לוגים. בעל שכבות מחיר (Hot/Cool/Archive) לפי תדירות הגישה.

📁

Azure Files

🏠 Private IP מול 🌍 Public IP

כתובת פרטית (Private IP) — כמו מספר דירה בתוך בניין: שימושית רק בתוך אותה הרשת, ואינה נגישה ישירות מהאינטרנט.

🛡️ Firewall ו-📖 DNS בשתי מילים

Firewall (חומת אש) הוא כמו מאבטח בכניסה לבניין עם רשימה: "מי מותר לו להיכנס/לצאת, ולאן". הוא בודק כל בקשת תקשורת מול חוקים מוגדרים מראש.


DNS הוא "ספר הטלפונים" של האינטרנט — הוא הופך שמות קריאים לבני אדם (כמו microsoft.com) לכתובות IP שהמחשבים באמת צריכים כדי לתקשר.

🎯 סיכום לפני שממשיכים

ברגע שהמושגים האלה ברורים — IP, Private/Public, CIDR, Port, Firewall, DNS — אפשר להבין כל שירות רשת ב-Azure, כי כולם בנויים סביבם.

// 08 — הרכיב המרכזי

Virtual Network — VNet

ה-"בניין המשרדים הפרטי" שלכם בתוך הענן — הבסיס שעליו נבנה כל מה שאחר.

🏢 מה זה VNet?

Virtual Network (VNet) היא רשת פרטית ומבודדת שאתם יוצרים בתוך Azure — כמו לשכור קומה שלמה בבניין ולבנות בה חדרים לפי הצורך שלכם. שום דבר לא נכנס או יוצא ממנה בלי שתאפשרו זאת.


ל-VNet מגדירים טווח כתובות (Address Space), למשל 10.0.0.0/16, ואז מחלקים אותו ל-Subnets (תתי-רשת) — ה"חדרים" בתוך הקומה.

📐 חוקים חשובים על VNet

  • VNet שייך לרג'ין אחד בלבד ולא יכול להתפרס על כמה רג'ינים
  • כל Subnet בתוכו הוא תת-קבוצה של הכתובות של ה-VNet, ואינו יכול לחפוף לתת-רשת אחרת
  • מחשבים (VMs) ומשאבים מקבלים כרטיס רשת (NIC) עם כתובת IP מתוך ה-Subnet
  • שתי VNets עם טווחי כתובות חופפים לא יכולות להתחבר זו לזו (Peering) — צריך טווחים שונים

⚠️ טריק שחשוב לדעת: Azure "גונב" 5 כתובות מכל Subnet

בניגוד לרשת ביתית, Azure שומר לעצמו 5 כתובות בכל Subnet לשימוש פנימי (כתובת הרשת, שער ברירת מחדל, שתי כתובות DNS פנימיות, וכתובת ה-Broadcast). לכן ב-Subnet בגודל /24 (256 כתובות) — יש בפועל 251 כתובות זמינות למחשבים שלכם.

🏢 VNet: 10.0.0.0/16 (סה"כ 65,536 כתובות) — West Europe
🚪 Subnet "Frontend": 10.0.1.0/24 — שרתי אתר
🗄️ Subnet "Backend": 10.0.2.0/24 — מסדי נתונים
🔥 Subnet "AzureFirewallSubnet": 10.0.3.0/26 — חומת אש
🔌 Subnet "GatewaySubnet": 10.0.4.0/27 — VPN/ExpressRoute Gateway
# יצירת VNet עם Subnet ראשון:
az network vnet create \
--resource-group MyRG --name MyVNet \
--address-prefix 10.0.0.0/16 \
--subnet-name Frontend --subnet-prefix 10.0.1.0/24

# הוספת Subnet נוסף לאותו VNet:
az network vnet subnet create \
--resource-group MyRG --vnet-name MyVNet \
--name Backend --address-prefix 10.0.2.0/24
// 09 — אבטחת רשת

Network Security Group — ה"מאבטח" של הרשת

מי מותר לו להיכנס ולצאת מכל Subnet או כרטיס רשת.

🛡️ מה זה NSG?

Network Security Group (NSG) היא רשימת חוקים (כמו רשימת המאבטח) שמצמידים ל-Subnet או לכרטיס רשת (NIC) של VM. כל חוק מגדיר: מאיפה, לאן, באיזה פורט, ואיזה פרוטוקול — ואם להתיר (Allow) או לחסום (Deny).


NSG הוא Stateful — אם התרתם בקשה נכנסת, התשובה שלה יוצאת אוטומטית מבלי צורך בחוק נפרד.

🔢 סדר עדיפויות (Priority)

לכל חוק יש מספר Priority בין 100 ל-4096. ככל שהמספר נמוך יותר — הוא נבדק ראשון. ברגע שנמצאה התאמה לחוק, Azure מפסיק לבדוק חוקים נוספים.

שם ברירת מחדלPriorityמה הוא עושה
AllowVNetInBound65000מתיר תעבורה בין משאבים באותו VNet
AllowAzureLoadBalancerInBound65001מתיר בדיקות תקינות מ-Load Balancer
DenyAllInBound65500חוסם כל תעבורה נכנסת אחרת מהאינטרנט — כברירת מחדל!
AllowVNetOutBound / AllowInternetOutBound65000-65001מתיר יציאה חופשית לרשת/לאינטרנט

💡 המסקנה החשובה ביותר

בברירת מחדל, שום דבר לא נכנס ל-Subnet חדש מהאינטרנט — אתם חייבים ליצור חוק Allow מפורש (למשל: "התר RDP רק מכתובת ה-IP הביתית שלי"). לעומת זאת, יציאה החוצה מותרת אוטומטית.

🏷️ Application Security Group (ASG)

במקום לכתוב כללי NSG לכל כתובת IP בנפרד, אפשר לקבץ כמה כרטיסי רשת תחת ASG (למשל "WebServers") ולכתוב חוק אחד שמתייחס לכל הקבוצה. נוח מאוד כשמוסיפים/מסירים שרתים.

🌐 Public IP — Standard SKU בלבד

חשוב לדעת: כתובות IP ציבוריות מסוג Standard הן מאובטחות כברירת מחדל — חסומות לחלוטין עד שתגדירו NSG שמתיר גישה. (מסוג Basic, הישן יותר, יצא משימוש והוחלף לגמרי ב-Standard).

# יצירת NSG וחוק שמתיר RDP רק מכתובת IP ספציפית:
az network nsg create --resource-group MyRG --name MyNSG

az network nsg rule create \
--resource-group MyRG --nsg-name MyNSG \
--name Allow-RDP-FromHome --priority 100 \
--source-address-prefixes 203.0.113.5/32 \
--destination-port-ranges 3389 \
--protocol Tcp --access Allow

Peering ו-Routing

איך שתי VNets מדברות ביניהן, ואיך שולטים בדיוק לאן התעבורה הולכת.

🔗 VNet Peering

Peering מחבר שתי VNets כך שהמשאבים בהן יכולים לדבר ביניהם באמצעות כתובות IP פרטיות — התעבורה עוברת ברשת הפנימית של מיקרוסופט ולא דרך האינטרנט הציבורי, מהר ומאובטח.


אפשר לחבר VNets גם בין רג'ינים שונים (Global Peering).

⚠️ Peering לא טרנזיטיבי!

אם VNet A מחובר ל-B, ו-B מחובר ל-C — A לא יכול "לעבור דרך" B כדי להגיע ל-C אוטומטית. לצורך חיבורים מורכבים בין הרבה VNets (טופולוגיית Hub-Spoke) נהוג להשתמש ב-Azure Firewall או Virtual WAN שמנתבים תעבורה במרכז.

טופולוגיית Hub-Spoke נפוצה: כל התעבורה בין ה-Spokes וגם החוצה עוברת דרך ה-Hub לבדיקה מרכזית

🗺️ Route Table (UDR — User Defined Route)

Azure כבר יודע לנתב תעבורה אוטומטית (System Routes) — למשל בין Subnets באותו VNet, או לאינטרנט. Route Table מאפשר לדרוס את ברירת המחדל ולהגיד: "כל תעבורה מסוימת — תעבור קודם דרך X".

🔥 שימוש נפוץ: כפיית תעבורה דרך Firewall

החוק הנפוץ ביותר: 0.0.0.0/0 → הכתובת הפרטית של Azure Firewall. כך כל תעבורה יוצאת מה-Subnet (לכל יעד) עוברת קודם דרך חומת האש לבדיקה, במקום לצאת ישירות.

# יצירת Peering בין שני VNets (משני הכיוונים):
az network vnet peering create --name HubToSpokeA \
--resource-group MyRG --vnet-name HubVNet \
--remote-vnet SpokeAVNet --allow-vnet-access

# יצירת Route Table שמפנה הכל דרך ה-Firewall:
az network route-table create --resource-group MyRG --name ToFirewall
az network route-table route create --resource-group MyRG \
--route-table-name ToFirewall --name DefaultToFW \
--address-prefix 0.0.0.0/0 --next-hop-type VirtualAppliance \
--next-hop-ip-address 10.0.3.4

חיבור On-Prem ↔ Azure

איך מחברים משרד פיזי, בית או מרכז נתונים קיים לרשת שב-Azure.

🌐 Public IP ו-🚪 NAT Gateway

Public IP נותן למשאב כתובת גלויה לאינטרנט (למשל ל-Load Balancer או VM שצריך להיות נגיש מבחוץ).


NAT Gateway פותר בעיה הפוכה: איך VMs פרטיים יוצאים לאינטרנט (לעדכונים, API חיצוני) בלי לתת לכל אחד מהם כתובת ציבורית משלו. ה-NAT Gateway "מלווה" את כל היציאה דרך כתובת ציבורית אחת משותפת, ומונע גם בעיית אזילת פורטים (SNAT exhaustion).

🔐 VPN Gateway

VPN Gateway יוצר מנהרה מוצפנת מעל האינטרנט הציבורי הרגיל, בין הרשת שלכם ל-VNet:

  • Site-to-Site (S2S) — מחבר משרד/מרכז נתונים שלם ל-Azure
  • Point-to-Site (P2S) — מחבר מחשב בודד (עובד מהבית) ישירות ל-VNet
  • VNet-to-VNet — מחבר שני VNets (חלופה ל-Peering, למשל בין ענני Azure שונים)

🚄 ExpressRoute — קו פרטי, לא דרך האינטרנט בכלל

ExpressRoute הוא חיבור פיזי ייעודי בין הרשת שלכם ל-Azure, דרך ספק תקשורת שותף — ללא מעבר כלשהו באינטרנט הציבורי. התוצאה: אמינות גבוהה יותר, השהיה (Latency) נמוכה ויותר יציבה, ורוחב פס גדול. יקר יותר מ-VPN אבל קריטי לארגונים גדולים או לתעבורה רגישה (למשל רפליקציה בין Domain Controllers מקומיים לענן).

מאפייןVPN GatewayExpressRoute
עובר דרךאינטרנט ציבורי (מוצפן)קו פרטי ייעודי דרך ספק
זמן הקמהדקות עד שעותשבועות (תלוי בספק)
עלותנמוכה יחסיתגבוהה יותר
מתאים לעסקים קטנים-בינוניים, חיבור מהירארגונים גדולים, תעבורה קריטית ורגישה
# יצירת NAT Gateway ליציאה לאינטרנט בלי חשיפת VMs:
az network public-ip create --resource-group MyRG --name NatIP --sku Standard
az network nat gateway create --resource-group MyRG --name MyNAT \
--public-ip-addresses NatIP
az network vnet subnet update --resource-group MyRG --vnet-name MyVNet \
--name Backend --nat-gateway MyNAT

⚖️ Load Balancer — "השוטר בצומת"

מפזר חיבורי רשת (TCP/UDP) בין כמה שרתים לפי כללים פשוטים (למשל Round Robin), בלי להסתכל בכלל על תוכן ה-HTTP. מהיר מאוד ומתאים לכל סוג תעבורה.

🚪 Application Gateway — "הפקידה שבודקת את הטופס"

מבין HTTP/HTTPS ויכול לנתב לפי כתובת ה-URL או הדומיין (למשל /api לשרת אחד ו-/images לשרת אחר), ומגיע עם WAF (חומת אש לאפליקציות ווב) מובנה.

🌍 Azure Front Door — הדלת הראשית העולמית

פועל בקצוות הרשת של מיקרוסופט ברחבי העולם (Anycast) — משתמש מתחבר לנקודה הקרובה אליו גיאוגרפית, ומשם מנותב פנימה לרג'ין הקרוב שבו רץ השירות שלכם. כולל גם CDN (Cache לתוכן סטטי) ו-WAF.

📖 Traffic Manager — "מכוון תנועה ברמת ה-DNS בלבד"

לא רואה תעבורה בפועל — הוא רק עונה לשאלת DNS "לאן לפנות" (למשל לפי רג'ין הכי קרוב, או Failover אם רג'ין שלם נופל). שימושי גם לפרוטוקולים שאינם HTTP.

// 13 — גישה פרטית לשירותים

Private Link ו-Service Endpoints

איך ניגשים לשירותי PaaS (כמו Storage או SQL) בלי לצאת בכלל לאינטרנט הציבורי.

🤔 הבעיה

שירותי PaaS כמו Azure Storage או Azure SQL Database נגישים לרוב דרך כתובת ציבורית (עם אימות, אך עדיין דרך האינטרנט). לפעמים רוצים שהתעבורה מה-VNet לשירות כזה תישאר לגמרי פרטית.

🔒 Private Endpoint

יוצר כרטיס רשת עם כתובת IP פרטית בתוך ה-Subnet שלכם, שמצביע ישירות על שירות ה-PaaS הספציפי. מבחינת שאר ה-VNet, השירות "נראה" כמו עוד משאב פנימי רגיל. אפשר גם לחסום גישה ציבורית לגמרי לשירות.

🛣️ Service Endpoint

פתרון פשוט וישן יותר: מרחיב את "הזהות" של ה-VNet לשירות, כך שהתעבורה נשארת ברשת הפנימית של מיקרוסופט — אבל השירות עדיין עונה על כתובת ציבורית, ולא מקבל כתובת פרטית ייעודית משלו.

// 14 — פתרון שמות

Azure DNS

איך שמות דומיין מתורגמים לכתובות IP — גם בציבור וגם בתוך הרשת הפרטית.

🌍 Azure DNS (Public Zones)

שירות שמאפשר לארח את רשומות ה-DNS של דומיין ציבורי שלכם (למשל mycompany.com) ישירות ב-Azure — עם ביצועים גבוהים וזמינות עולמית.

🏠 Azure Private DNS Zone

פותר שמות בתוך ה-VNet בלבד — למשל לתת לשרת פנימי שם קריא כמו db01.internal.local במקום לזכור כתובת IP. אפשר לחבר את אותו Private DNS Zone לכמה VNets, וגם הוא חיוני לעבודה נכונה עם Private Endpoint (כדי שהשם הציבורי של השירות "יפנה" לכתובת הפרטית).

💡 חיבור בין הנושאים

זוכרים את "ספר הטלפונים" מיסודות הרשת? זה בדיוק מה ש-DNS עושה גם כאן — רק שעכשיו יש לנו שני "ספרים": אחד לעולם החיצון (Public Zone) ואחד פנימי לרשת הפרטית שלכם (Private Zone).

// 15 — הגנה מתקדמת

Azure Firewall, WAF ו-DDoS

כשה-NSG הפשוט לא מספיק — כלי האבטחה המתקדמים יותר של Azure.

🔥 Azure Firewall

חומת אש מנוהלת (לא צריך לתחזק שרת בעצמכם), ברמת רשת ואפליקציה, ממוקמת בדרך כלל ב-Hub של טופולוגיית Hub-Spoke. יודעת לסנן גם לפי שם דומיין (FQDN) ולא רק IP — למשל "התר גישה רק ל-*.windowsupdate.com".

🌐 WAF — Web Application Firewall

מגן ספציפית על אפליקציות ווב מפני התקפות ברמת האפליקציה — כמו SQL Injection או XSS — על בסיס כללים סטנדרטיים (OWASP). מתחבר ל-Application Gateway או ל-Front Door.

🛡️ DDoS Protection

Basic — פעיל אוטומטית וללא עלות על כל משאב ב-Azure, מגן מפני התקפות נפוצות ברמת התשתית.
Standard — בתשלום, עם מדיניות מותאמת למשאבים שלכם, ניטור מפורט, דוחות התקפה, ואף הגנה כספית (Cost Protection) אם התקפה גורמת ל-Scale-out יקר.

// 16 — תרגול

מעבדה — Hands-On

שישה תרגילים הדרגתיים, מהבסיס ועד טופולוגיה ארגונית מלאה.

1
יצירת VNet עם שני Subnets
קל
  • בפורטל: Create a resource → Virtual Network
  • תנו שם, בחרו Region, והגדירו Address space כ-10.0.0.0/16
  • הוסיפו Subnet בשם "web" בטווח 10.0.1.0/24
  • הוסיפו Subnet שני בשם "data" בטווח 10.0.2.0/24
  • צרו, ובדקו את התוצאה תחת "Diagram" בעמוד ה-VNet
2
NSG שחוסם RDP מכולם חוץ מכם
קל
  • בדקו מה כתובת ה-IP הציבורית שלכם (חיפוש "what is my ip")
  • צרו NSG חדש וצרפו אותו ל-Subnet "web"
  • הוסיפו חוק Inbound: Allow, פורט 3389, מקור = כתובת ה-IP שלכם בלבד, Priority 100
  • ודאו ש-DenyAllInBound (65500) עדיין קיים ולא נמחק
  • נסו לגשת מ-IP אחר (למשל דרך VPN) וודאו שנחסם
3
Peering בין שתי VNets ובדיקת קישוריות
בינוני
  • צרו VNet שני עם טווח שאינו חופף (למשל 10.1.0.0/16)
  • הגדירו Peering בשני הכיוונים בין ה-VNets
  • פרסו VM קטן בכל VNet (בלי Public IP)
  • התחברו ל-VM הראשון (למשל דרך Azure Bastion) ונסו לפנות ל-IP הפרטי של השני
  • ודאו שהתקשורת עוברת — סימן ש-Peering תקין
4
יציאה לאינטרנט בלי Public IP — NAT Gateway
בינוני
  • פרסו VM ללא Public IP כלל בתוך Subnet קיים
  • צרו Public IP חדש מסוג Standard
  • צרו NAT Gateway וחברו אליו את ה-Public IP
  • שייכו את ה-NAT Gateway ל-Subnet של ה-VM
  • מתוך ה-VM, בצעו בקשת יציאה (למשל curl לאתר בדיקת IP) וודאו שמוצג ה-IP של ה-NAT
5
טופולוגיית Hub-Spoke עם Azure Firewall
מתקדם
  • צרו Hub VNet עם Subnet מיוחד בשם המדויק "AzureFirewallSubnet" (לפחות /26)
  • פרסו בו Azure Firewall וקבלו את ה-IP הפרטי שלו
  • צרו שני Spoke VNets, כל אחד Peering אל ה-Hub
  • צרו Route Table בכל Spoke עם חוק 0.0.0.0/0 → IP הפרטי של ה-Firewall, וצרפו ל-Subnets
  • הגדירו כלל ב-Firewall שמתיר תעבורה בין ה-Spokes, ובדקו בלוגים שהיא אכן עוברת דרכו
6
Private Endpoint לחשבון אחסון וחסימת גישה ציבורית
מתקדם
  • צרו Storage Account ונטרלו בו "Public network access"
  • צרו Private Endpoint בתוך ה-VNet, מקושר ל-Storage Account (Sub-resource: blob)
  • אשרו את החיבור (אם לא אושר אוטומטית) וצרו Private DNS Zone בשם privatelink.blob.core.windows.net
  • קשרו את ה-Private DNS Zone ל-VNet שלכם
  • מתוך VM בתוך ה-VNet, בדקו ששם ה-Storage Account פונה לכתובת פרטית — ושגישה מבחוץ נחסמת
