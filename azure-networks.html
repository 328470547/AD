// 01 — ממש מהיסוד

מה זה בכלל "ענן"?

לפני ש-Azure יעזור לנו — צריך להבין מה זה מחשוב ענן בכלל, בלי מונחים מפחידים.

🖥️ נתחיל מהבסיס — מה זה שרת?

שרת (Server) הוא בפשטות מחשב חזק שנשאר דלוק כל הזמן ומספק שירות למחשבים אחרים — למשל, מחשב ששומר אתר אינטרנט, או מחשב ששומר את המסמכים של החברה.


בעבר, כל חברה קנתה שרתים משלה, שמה אותם בחדר מיוחד (Data Center פרטי) ותחזקה אותם בעצמה. זה נקרא On-Premises (On-Prem) — "אצלנו בבית".

☁️ אז מה זה "ענן"?

"ענן" הוא לא באמת ענן באוויר — זה פשוט המחשב של מישהו אחר, שיושב במרכז נתונים ענק (Data Center) שבבעלות חברה כמו Microsoft, Amazon או Google, ומחובר לאינטרנט.


במקום לקנות שרת ולתחזק אותו בעצמך, אתה שוכר חלקיק ממחשב ענק כזה, דרך האינטרנט, ומשלם רק על מה שאתה באמת משתמש בו — בדיוק כמו חשבון חשמל.

🌍 מה זה בדיוק Microsoft Azure?

Azure הוא פלטפורמת הענן הציבורי של Microsoft — מאות מרכזי נתונים ברחבי העולם, המחוברים ביניהם ברשת פרטית ענקית של מיקרוסופט, ומציעים אלפי שירותים: שרתים וירטואליים, מסדי נתונים, אחסון, בינה מלאכותית — וכמובן, רשתות, שבהן נתמקד במדריך הזה.


המתחרות העיקריות: AWS (אמזון) ו-Google Cloud (GCP). כולן עובדות על אותו רעיון בסיסי.

🌍 שלושה סוגי ענן: Public, Private ו-Hybrid

כשמדברים על "ענן", לא תמיד מתכוונים לאותו דבר בדיוק. יש שלושה סוגים עיקריים:

  • Public Cloud (ענן ציבורי) — זה מה שדיברנו עליו עד עכשיו: תשתית משותפת בבעלות ספק כמו מיקרוסופט, שמשרתת הרבה לקוחות שונים על אותה תשתית פיזית (כל אחד מבודד לגמרי מהאחרים). זה Azure "הרגיל".
  • Private Cloud (ענן פרטי) — תשתית שמיועדת לארגון אחד בלבד ולא משותפת עם אף אחד אחר. יכולה לשבת פיזית אצל הארגון עצמו, או אצל ספק שמייעד אותה בלעדית עבורו.
  • Hybrid Cloud (ענן היברידי) — שילוב של השניים: חלק מהתשתית נשארת On-Premises (אצל הארגון), וחלק עוברת לענן הציבורי — כשהשתיים מחוברות זו לזו ועובדות יחד כמערכת אחת.

שימו לב: Hybrid Cloud הוא בדיוק המקום שבו כל מה שלמדתם על VPN Gateway ו-ExpressRoute נכנס לתמונה — הם הכלים שמחברים בפועל בין העולם הפרטי לעולם הציבורי.

💡 למה זה חשוב להבין את הרשת דווקא?

אפשר לחשוב על Azure כמו עיר ענקית: יש בה בניינים (שרתים ושירותים), אבל בלי כבישים, כתובות ושילוט — אף אחד לא יכול להגיע לאף מקום. הרשת ב-Azure היא בדיוק זה: הכבישים, הגבולות, השערים והמאבטחים שקובעים מי יכול לדבר עם מי, מאיפה ולאן. זה הבסיס לכל דבר אחר שתבנו בענן.

💼 דוגמה מהעולם האמיתי

סטארטאפ ישראלי קטן שרוצה להשיק אתר לא צריך לקנות שרת ב-20,000 ₪ ולחכות שבועיים להתקנה — הוא פותח חשבון Azure, מקים שרת וירטואלי תוך חמש דקות, ומשלם רק על השעות שבהן הוא פעיל. וכשהאתר מצליח וביום ההשקה מגיע פי 10 יותר תנועה מהצפוי — אפשר להגדיל את השרת (Scale Up) תוך דקות, בלי לקנות חומרה חדשה.

// 02 — ארגון וניהול

איך Azure מאורגן?

לפני שנכנסים לרשתות — צריך להבין את "התיקיות" שבתוכן הכל נשמר.

🏢 Management Group (קבוצת ניהול) — "כל הארגון"
💳 Subscription (מנוי) — "כרטיס האשראי / יחידת חיוב"
📁 Resource Group (קבוצת משאבים) — "תיקייה"
🖥️ Resource (משאב) — VNet, VM, Storage Account...
🌐 Resource — עוד VNet, NSG...

📁 Resource Group — "תיקייה" למשאבים

Resource Group (RG) הוא פשוט תיקייה לוגית שבה שמים משאבים ששייכים יחד — למשל, כל מה שקשור לאתר אחד: השרת, הרשת, מסד הנתונים. מוחקים את ה-RG — מוחקים הכל שבתוכו.

💳 Subscription — יחידת חיוב וגבול הרשאות

Subscription קובע מי משלם ומהו התקציב/המכסה. זה גם גבול אבטחה חשוב — לכל Subscription יש הרשאות (RBAC) נפרדות. ארגון יכול להחזיק כמה מנויים (למשל: פיתוח, בדיקות, ייצור).

🌍 Region — איפה פיזית יושב המשאב

Region הוא אזור גיאוגרפי שבו יש מרכזי נתונים של מיקרוסופט — לדוגמה West Europe (הולנד) או East US. כשיוצרים משאב, בוחרים באיזה Region הוא יחיה. חשוב: משאבי רשת (כמו VNet) שייכים ל-Region אחד בלבד.

🏗️ Availability Zone — הגנה מתקלות

בתוך רוב ה-Regions הגדולים יש כמה Availability Zones — מרכזי נתונים נפרדים פיזית עם חשמל, קירור וחיבור אינטרנט משלהם. פורסים משאבים על פני כמה Zones כדי שאם אחד נופל, השירות ממשיך לרוץ.

🔗 Region Pair — "זוג גיבוי" גיאוגרפי

לרוב ה-Regions יש "אח תאום" רחוק ממנו מספיק (בדרך כלל באותה מדינה/יבשת), המיועד לגיבוי ואסון — למשל West Europe (הולנד) מזווג עם North Europe (אירלנד). זה שימושי לתכנון Disaster Recovery.

# יצירת Resource Group חדש דרך Azure CLI:
az group create --name MyRG --location westeurope

# הצגת כל ה-Subscriptions הזמינים:
az account list --output table

💼 דוגמה מהעולם האמיתי

חברת פינטק מקימה שלושה Subscriptions נפרדים תחת אותו Tenant — אחד ל-Dev, אחד ל-Test ואחד ל-Production — כדי שמפתח שטועה בסביבת הפיתוח לא יוכל בטעות למחוק משאב בסביבת הייצור. כל המשאבים שלה יושבים ברג'ין West Europe בגלל רגולציית GDPR שמחייבת לשמור מידע לקוחות אירופאים בתוך אירופה בלבד.

// 03 — הכלים לניהול

איך מנהלים את כל זה?

ארבע דרכים שונות "לדבר" עם Azure, ושתי שכבות ממשל ששומרות על סדר כשהארגון גדל.

🖱️ Azure Portal

ממשק האינטרנט הגרפי הרשמי לניהול Azure — לוחות בקרה (Dashboards), אשפים ליצירת משאבים, גרפים לניטור וניהול משתמשים. הכי נוח למי שרק מתחיל או לבדיקה חד-פעמית, אבל לא מתאים לפעולות חוזרות בקנה מידה גדול.

⌨️ Azure CLI ו-Azure PowerShell

שתי דרכים "לתכנת" את הניהול מתוך טרמינל: Azure CLI (פקודות בסגנון az ..., חוצה מערכות הפעלה) ו-Azure PowerShell (מודול Az, מתאים למי שכבר מכיר PowerShell). שניהם מאפשרים לכתוב סקריפטים ולחזור על אותה פעולה במדויק פעמים רבות — בדיוק כמו הפקודות שראיתם כבר בכל המדריך הזה.

⚙️ Azure Resource Manager (ARM) — המנוע שמאחורי הכל

בין אם משתמשים בפורטל, ב-CLI או ב-PowerShell — כולם בסוף פונים לאותה שכבה: ARM. זהו המנוע שמקבל בקשה ("תיצור לי VNet כזה") ומבצע אותה בפועל. אפשר גם לכתוב את כל התצורה הרצויה מראש בקובץ (ARM Template בפורמט JSON, או Bicep — שפה נוחה יותר שמתורגמת ל-ARM) ולהריץ אותו — גישה שנקראת Infrastructure as Code (IaC): הרשת והמשאבים שלכם מתועדים כקוד, ניתנים לשחזור ולביקורת בדיוק כמו כל קוד אחר.

📜 Azure Policy — שומר הסדר הארגוני

מנגנון שאוכף חוקים על כל מה שנוצר ב-Subscription — למשל: "אסור ליצור משאבים מחוץ ל-Israel Central", "כל VM חייב תגית Owner", או "אסור ליצור Public IP מסוג Basic". פוליסה יכולה רק להתריע (Audit) או גם לחסום יצירה בפועל (Deny) — כלי הממשל (Governance) המרכזי של Azure.

🏢 Tenant מול Subscription — לא לבלבל!

Tenant הוא גבול הזהות של הארגון — ספרייה יחידה ב-Microsoft Entra ID שמכילה את כל המשתמשים וההרשאות שלכם. Subscription הוא גבול החיוב וההרשאות למשאבים, וחי בתוך Tenant אחד. ארגון אחד = בדרך כלל Tenant אחד, אך יכול להכיל בתוכו הרבה Subscriptions (לפי מחלקות, סביבות וכו').

📦 Azure Blueprints — היה, ולאן זה עבר

בעבר, Azure Blueprints שימש לארוז יחד תבניות ARM, פוליסות והרשאות לפריסה אחידה של סביבות תואמות-רגולציה. מיקרוסופט הוציאה את השירות משימוש (Retired), וכיום הדרך המומלצת היא שילוב של Template Specs ו-Deployment Stacks יחד עם Azure Policy — שווה לדעת את השם הישן אם נתקלים בו בתיעוד או בסביבות ותיקות.

🎁 בונוס: איך יודעים שהכל תקין, ושלא משלמים יותר מדי?

שלושה כלים משלימים חשובים לניהול יומיומי:

  • Azure Monitor ו-Log Analytics — אוספים מדדי ביצועים ולוגים מכל הסביבה, כדי שתדעו מה קורה בפועל ותקבלו התראה כשמשהו משתבש, לפני שמשתמשים בכלל שמים לב.
  • Azure Advisor — סורק את הסביבה שלכם ונותן המלצות אישיות, כמו "השרת הזה בקושי בשימוש — אפשר להקטין אותו ולחסוך כסף".
  • Cost Management — עוקב אחרי ההוצאה החודשית שלכם, ומאפשר להגדיר תקציבים והתראות אם ההוצאה חורגת מהצפוי.

💼 דוגמה מהעולם האמיתי

צוות תשתיות שמנהל 40 סביבות זהות ללקוחות שונים כותב את כל התצורה (VNet, NSG, VM) כקובץ Bicep אחד. כשצריך לעדכן חוק אבטחה בכל הסביבות — במקום להיכנס ידנית ל-40 מקומות בפורטל, משנים שורה אחת בקוד ומריצים Deployment אחד לכולם. Azure Policy חוסם כל ניסיון של מפתח ליצור משאב מחוץ לרג'ין המאושר.

// 04 — מי אתה ומה מותר לך

אבטחה וניהול זהויות

מי מורשה להיכנס, מאיפה, ומה קורה אם משהו חשוד קורה.

🪪 Microsoft Entra ID (לשעבר Azure AD)

שירות ניהול הזהויות המרכזי של Azure — הוא ה"ספר הטלפונים" שיודע מי המשתמשים, הקבוצות והאפליקציות בארגון, ומה מותר לכל אחד מהם. הוא זה שמאמת אתכם כשאתם נכנסים לפורטל, ומה שמאפשר Single Sign-On (SSO) ו-MFA (אימות דו-שלבי) בכל שירותי מיקרוסופט וגם באפליקציות חיצוניות. (השם שונה מ-"Azure Active Directory" ל-Microsoft Entra ID — אותו שירות, שם חדש.)

🚦 Conditional Access

מנגנון חוקים שמחליט בזמן אמת אם להתיר כניסה — לא רק לפי סיסמה נכונה, אלא גם לפי מאיפה מתחברים (מדינה), מאיזה מכשיר (מנוהל/לא מנוהל), ורמת סיכון ההתחברות. לדוגמה: "דרוש MFA אם ההתחברות מגיעה ממדינה לא מוכרת", או "חסום גישה ממכשירים שלא עומדים במדיניות הארגון".

🌍 Microsoft Entra External ID (לשעבר Azure AD B2C)

בעוד Entra ID "הרגיל" מנהל עובדים פנימיים, External ID מנהל זהויות של לקוחות חיצוניים — למשל משתמשים שנרשמים לאפליקציית מובייל או לאתר מסחר. מאפשר התחברות עם Google, Facebook או אימייל רגיל, בלי לתת להם גישה לשום דבר פנימי בארגון.

🔗 Microsoft Entra Domain Services (AAD DS)

שירות מנוהל שנותן יכולות בסגנון Active Directory מוכר — Kerberos, NTLM, LDAP ומדיניות דמויות GPO — בלי להקים ולתחזק Domain Controllers בעצמכם. שימושי בעיקר להעברת אפליקציות ותיקות (Legacy) לענן מבלי לשכתב אותן מחדש, ובתרחישים היברידיים יחד עם ה-AD המקומי (On-Prem) שלכם.

🛡️ Microsoft Defender for Cloud

פלטפורמת אבטחה שסורקת את כל הסביבה (וגם היברידית/רב-ענן) ונותנת Secure Score — ציון המשקף כמה אתם חשופים, עם המלצות קונקרטיות לתיקון. כוללת גם הגנת זמן-ריצה (Workload Protection) על VMs, מאגרי מידע ומכולות.

🔑 Azure Key Vault

כספת דיגיטלית מרכזית לאחסון סודות, מפתחות הצפנה ותעודות (Certificates) — כדי שאפליקציות לא ישמרו סיסמאות או API Keys בקוד המקור. גישה נשלטת בהרשאות מדויקות, וכל שימוש נרשם ביומן ביקורת.

🕵️ Microsoft Sentinel — ה"חדר בקרה" הביטחוני

SIEM/SOAR מבוסס ענן — אוסף לוגים והתראות מכל הסביבה (Azure, On-Prem, ואפילו עננים אחרים), מזהה דפוסי התקפה חשודים באמצעות ניתוח וכללים חכמים, ויכול אף להפעיל תגובה אוטומטית (למשל: לנתק אוטומטית משתמש שנחשד בפריצה). זהו הכלי שרואה את "התמונה המלאה" מכל שאר כלי האבטחה יחד.

💡 איך כל זה מתחבר יחד

Entra ID קובע מי אתם. Conditional Access קובע באילו תנאים מותר לכם להיכנס. Key Vault שומר את הסודות שהאפליקציות שלכם צריכות. Defender for Cloud בודק שההגדרות שלכם תקינות. Sentinel צופה על הכל ומתריע אם משהו חורג. זו הגנה בשכבות (Defense in Depth).

💼 דוגמה מהעולם האמיתי

בנק מחייב MFA לכל עובד שמתחבר מרשת שאינה רשת הבנק, וחוסם לחלוטין גישה ממדינות בסיכון גבוה באמצעות Conditional Access. כשעובד עוזב את הארגון, מנטרלים את החשבון שלו ב-Entra ID — ומיידית הוא מאבד גישה לכל 200 האפליקציות שהיו מחוברות אליו דרך Single Sign-On, במקום לבטל גישה ידנית בכל מערכת בנפרד.

// 05 — היכן הקוד באמת רץ

מחשוב ב-Azure — Compute

מ"שרת וירטואלי רגיל" ועד קוד שרץ לשניות בודדות בלי שרת בכלל.

🖥️

Azure Virtual Machines

שרת וירטואלי מלא (IaaS) — שליטה מוחלטת על מערכת ההפעלה, בדיוק כמו שרת פיזי, רק בענן.

📈

Virtual Machine Scale Sets

קבוצת VMs זהים שגדלה ומצטמצמת אוטומטית לפי עומס (Auto Scaling) — בסיס לאתרים גדולים.

☸️

Azure Kubernetes Service (AKS)

Kubernetes מנוהל — מריץ אפליקציות ארוזות במכולות (Containers) בקנה מידה, בלי לנהל את השרתים בעצמכם.

🌐

Azure App Service

PaaS להרצת אתרים ו-APIs (.NET, Node.js, Python, Java...) — מעלים קוד, Azure מטפל בשרת, בגיבוי ובקנה המידה.

⚡

Azure Functions

קוד "חסר שרת" (Serverless) שרץ רק כשמפעילים אותו (למשל בקשת HTTP או קובץ חדש) — משלמים רק על זמן ריצה בפועל.

🔀

Azure Logic Apps

בניית תהליכים אוטומטיים בגרירה-והשלכה בין עשרות שירותים, כמעט בלי לכתוב קוד בכלל.

🧮

Azure Batch

הרצת עבודות חישוב מקבילות בקנה מידה ענק (HPC) — למשל עיבוד וידאו או סימולציות מדעיות על אלפי ליבות בו-זמנית.

🍕 חזרה לאנלוגיית הפיצה — איפה כל שירות נמצא

Virtual Machines = IaaS (אתם אחראים כמעט על הכל). App Service ו-AKS = PaaS (הפלטפורמה מוכנה, אתם רק מריצים עליה). Azure Functions ו-Logic Apps = Serverless (הקצה הכי "משוחרר" — אין בכלל שרת לחשוב עליו, רק הקוד/התהליך עצמו).

💼 דוגמה מהעולם האמיתי

אתר איקומרס שמקבל 90% מהתנועה השנתית שלו ב"יום שישי השחור" משתמש ב-VMSS כדי להוסיף אוטומטית עשרות שרתים בזמן העומס ולהוריד אותם בחזרה למחרת. לעומתו, חברה קטנה ששולחת התראת מייל פעם ביום מריצה זאת ב-Azure Functions ומשלמת אגורות בודדות בחודש — במקום להחזיק שרת שרץ 24/7 בשביל פעולה של שנייה אחת.

// 06 — איפה המידע נשמר

אחסון ומסדי נתונים

מקבצים גולמיים ועד מסדי נתונים גלובליים בקנה מידה ענק.

🗄️

Azure Storage Account

ה"מיכל" העל שמאחד תחתיו את שירותי האחסון: Blob, Files, Queues ו-Tables. כל דבר שנשמר ב-Azure שאינו מסד נתונים מובנה — עובר דרכו.

📦

Azure Blob Storage

אחסון לקבצים לא-מובְנים בכמויות עצומות — תמונות, וידאו, גיבויים, לוגים. בעל שכבות מחיר (Hot/Cool/Archive) לפי תדירות הגישה.

📁

Azure Files

שיתוף קבצים מנוהל בענן, נגיש כמו כונן רשת רגיל (פרוטוקול SMB/NFS) — מצוין להחלפת שרת קבצים ישן.

🗃️

Azure SQL Database

מסד נתונים יחסי מנוהל, מבוסס SQL Server — טבלאות, קשרים, שאילתות SQL רגילות, בלי לתחזק שרת בעצמכם.

🌐

Azure Cosmos DB

מסד נתונים NoSQL גלובלי ומבוזר, עם תמיכה במספר מודלים (MongoDB, Cassandra ועוד) והשהיה נמוכה בכל העולם.

🌡️ שכבות מחיר ב-Blob Storage

Hot — לגישה תכופה, יקר יותר לאחסון וזול לגישה. Cool — לנתונים שנגישים לעיתים רחוקות (חודש ומעלה). Archive — לארכיון ארוך טווח, הכי זול לאחסון אך לוקח שעות לשחזר קובץ ממנו. בחירה נכונה בין השכבות חוסכת עלויות משמעותיות.

💼 דוגמה מהעולם האמיתי

חברת ביטוח שמחויבת רגולטורית לשמור הקלטות שיחות שירות במשך 7 שנים שומרת את החודש האחרון ב-Hot Tier לגישה מהירה, ומעבירה אוטומטית כל מה שמעל 90 יום ל-Archive Tier — וחוסכת כך עשרות אחוזים בעלויות אחסון. אפליקציית משחק גלובלית משתמשת ב-Cosmos DB כדי שכל שחקן, בכל מדינה, יקבל תגובה תוך אלפיות שנייה מהשרת הקרוב אליו.

// פיתוח ותפעול

DevOps ו-CI/CD

איך צוותי פיתוח משחררים עדכונים לאתר או לאפליקציה שוב ושוב, מהר, ובלי הפתעות.

🤝 מה זה בכלל DevOps?

בעבר, בהרבה חברות, מי שכתב את הקוד (Developers) ומי שהפעיל את השרתים בפועל (Operations) היו שני צוותים נפרדים לגמרי, שכמעט לא דיברו זה עם זה. המפתחים "זרקו" קוד חדש מעל הגדר, והצוות התפעולי היה צריך להתמודד עם זה לבד — מה שגרם לעדכונים נדירים, מלחיצים, ולא פעם עם תקלות.


DevOps היא גישת עבודה (לא תוכנה ספציפית) שמאחדת בין שני הצדדים, כדי לשחרר עדכונים קטנים ותכופים בביטחון, במקום עדכון ענק ומפחיד פעם ברבעון.

🏭 אנלוגיה: פס ייצור אוטומטי

דמיינו מפעל מכוניות ישן, שבו כל רכיב נבדק ידנית בסוף הקו על ידי אדם — איטי, מייגע, וקל לפספס תקלה. עכשיו דמיינו פס ייצור מודרני, שבו כל רכיב נבדק אוטומטית ברגע שהוא מיוצר, לפני שהוא בכלל ממשיך לתחנה הבאה.


זה בדיוק מה ש-CI/CD עושה לתוכנה: כל שינוי קוד נבדק אוטומטית ברגע שהוא נכתב, במקום לחכות שיצטברו הרבה שינויים ואז לגלות תקלה שקשה לאתר מאיפה היא הגיעה.

🔄 CI לעומת CD — שני חצאים של אותו תהליך

CI (Continuous Integration) — "שילוב מתמשך". בכל פעם שמתכנת שומר שינוי קוד חדש, המערכת אוטומטית "בונה" את הקוד ומריצה עליו בדיקות, כדי לוודא שהוא לא שבר שום דבר. זה קורה הרבה פעמים ביום, ולא פעם בשבוע.


CD (Continuous Delivery / Deployment) — "אספקה מתמשכת". ברגע שהקוד עבר את כל הבדיקות, המערכת מכינה אותו אוטומטית לשחרור (Delivery), ולפעמים אפילו מעלה אותו ישירות לסביבת הייצור בלי מגע יד אדם (Deployment).

🧰 Azure DevOps — כל התהליך במקום אחד

Azure DevOps היא הפלטפורמה של מיקרוסופט לניהול כל מחזור החיים של פיתוח תוכנה תחת קורת גג אחת:

  • Repos — מקום לשמור את קוד המקור (מבוסס Git)
  • Boards — ניהול משימות ותכנון עבודה
  • Pipelines — האוטומציה שמריצה את ה-CI/CD בפועל
  • Artifacts — מקום לאחסן חבילות תוכנה מוכנות

⚙️ Azure Pipelines — מנוע האוטומציה

זהו הרכיב שמבצע בפועל את ה-CI/CD: כותבים קובץ הגדרות בפורמט YAML שמתאר את השלבים ("קודם תבנה, אחר כך תבדוק, לבסוף תפרוס"), והמערכת מריצה אותם אוטומטית בכל שינוי קוד. אפשר להשתמש בו גם עם קוד ששמור ב-GitHub, לא רק ב-Azure Repos.

🐙 GitHub Actions for Azure

הרבה צוותים כבר שומרים את הקוד שלהם ב-GitHub (לא ב-Azure DevOps). עבורם, GitHub Actions מציע דרך חלופית לאותו רעיון: תהליכי אוטומציה שמוגדרים ורצים ישירות בתוך מאגר הקוד ב-GitHub עצמו, כולל אפשרות לפרוס ישירות ל-Azure. זה חוסך את הצורך בכלי חיצוני נפרד — הכל נשאר במקום אחד שהצוות כבר מכיר.

💼 דוגמה מהעולם האמיתי

צוות פיתוח בחברת סטארטאפ שומר את הקוד שלו ב-GitHub. בכל פעם שמתכנת "דוחף" שינוי, GitHub Actions מריץ אוטומטית בדיקות, ואם הן עוברות — מפרסם את הגרסה החדשה ישירות לאתר הייצור תוך דקות, בלי שאף אחד יצטרך להתחבר ידנית לשרת. לעומת זאת, ארגון גדול יותר עם כמה צוותים ותהליכי אישור מורכבים משתמש ב-Azure DevOps Pipelines, שמאפשר גם שלבי אישור ידניים בין הבנייה לפריסה בפועל.

// נתונים ובינה מלאכותית

Data & AI

איך אוספים מידע ממקומות שונים, מנתחים אותו בקנה מידה ענק, ואפילו מלמדים מחשב לחזות איתו את העתיד.

🏭 Azure Data Factory (ADF) — פס הייצור של הנתונים

לארגון גדול יש בדרך כלל מידע במקומות שונים ומגוונים — מסד נתונים אחד, קובץ Excel שני, מערכת ענן שלישית. Azure Data Factory הוא שירות שאוסף נתונים מכל המקומות האלה, מעבד ומנקה אותם, ומעביר אותם למקום מרכזי אחד — תהליך שנקרא ETL.


אנלוגיה: זה כמו פס ייצור שאוסף חומרי גלם ממחסנים שונים, מעבד אותם לפי מתכון קבוע, ומעביר את התוצר המוגמר למחסן מרכזי — הכל בלי שאף אחד יצטרך לעשות זאת ידנית.

🔬 Azure Synapse Analytics — המעבדה לניתוח מידע ענק

אחרי שהמידע נאסף במקום אחד, לפעמים יש צורך לנתח כמויות עצומות ממנו בבת אחת (Big Data) — הרבה יותר ממה שמסד נתונים רגיל יכול להתמודד איתו ביעילות. Azure Synapse Analytics היא פלטפורמה שמשלבת כמה מנועי ניתוח (כולל SQL ו-Spark) כדי לחפור בתוך הררי מידע ולמצוא בהם דפוסים ותובנות, מהר.

🤖 Azure Machine Learning — כשהמחשב לומד לבד

מודל למידת מכונה (Machine Learning) הוא תוכנה שלא מקבלת חוקים ידניים מראש ("אם X אז Y"), אלא לומדת דפוסים מתוך כמויות גדולות של דוגמאות עבר, ולאחר מכן משתמשת במה שלמדה כדי לחזות או לסווג מידע חדש שהיא מעולם לא ראתה — למשל "האם העסקה הזו כנראה הונאה?" או "איזה מוצר הלקוח הזה כנראה ירצה?"


Azure Machine Learning הוא השירות שמאפשר לבנות, לאמן ולהפעיל מודלים כאלה, בלי שתצטרכו לבנות ולתחזק בעצמכם את כל תשתית החישוב הכבדה שדרושה לאימון.

🔗 איך שלושת השירותים מתחברים יחד

תהליך טיפוסי בארגון: Azure Data Factory אוסף ומנקה נתונים ממקורות שונים ⟵ Azure Synapse Analytics מנתח את כל הנתונים האלה בקנה מידה גדול ומוצא בהם דפוסים ⟵ Azure Machine Learning לומד מהדפוסים האלה ובונה מודל שיודע לחזות מה יקרה הלאה על מידע חדש.

💼 דוגמה מהעולם האמיתי

רשת חנויות אוספת מדי יום נתוני מכירות מכל הסניפים דרך Azure Data Factory, אל מחסן נתונים מרכזי אחד. בעונת החגים, המנתחים משתמשים ב-Azure Synapse Analytics כדי לגלות אילו מוצרים נמכרים הכי טוב באילו אזורים. ולבסוף, מודל שנבנה ב-Azure Machine Learning לומד מהיסטוריית המכירות ומנבא כמה מלאי כדאי להזמין לכל סניף לקראת החג הבא — בלי שאף אחד יצטרך לנחש ידנית.

כתובת ציבורית (Public IP) — כמו כתובת הרחוב של הבניין: כל העולם יכול לפנות אליה דרך האינטרנט.

כשרואים כתובת כמו 10.0.1.0/24 — המספר אחרי הקו הנטוי אומר "כמה כתובות" יש בקבוצה הזו. ככל שהמספר קטן יותר — יש יותר כתובות בקבוצה.

אם ה-IP הוא כתובת הבניין — ה-Port הוא מספר הדירה בתוכו: הוא אומר לאיזה "שירות" בתוך המחשב להפנות את התעבורה. אתר אינטרנט, למשל, "יושב" בפורט 443.

🛡️ Firewall ו-📖 DNS בשתי מילים

Firewall (חומת אש) הוא כמו מאבטח בכניסה לבניין עם רשימה: "מי מותר לו להיכנס/לצאת, ולאן". הוא בודק כל בקשת תקשורת מול חוקים מוגדרים מראש.


DNS הוא "ספר הטלפונים" של האינטרנט — הוא הופך שמות קריאים לבני אדם (כמו microsoft.com) לכתובות IP שהמחשבים באמת צריכים כדי לתקשר.

🎯 סיכום לפני שממשיכים

ברגע שהמושגים האלה ברורים — IP, Private/Public, CIDR, Port, Firewall, DNS — אפשר להבין כל שירות רשת ב-Azure, כי כולם בנויים סביבם.

💼 דוגמה מהעולם האמיתי

מנהל IT שרוצה לחסום גישה לאתר מסוים בכל המשרד לא חוסם כל כתובת IP של השרת (יש לו הרבה, והן משתנות) — הוא חוסם לפי שם הדומיין (DNS), שהרבה יותר יציב, או משתמש בפורט ובפרוטוקול הרלוונטיים.

// 08 — הרכיב המרכזי

Virtual Network — VNet

ה-"בניין המשרדים הפרטי" שלכם בתוך הענן — הבסיס שעליו נבנה כל מה שאחר.

🏢 מה זה VNet?

Virtual Network (VNet) היא רשת פרטית ומבודדת שאתם יוצרים בתוך Azure — כמו לשכור קומה שלמה בבניין ולבנות בה חדרים לפי הצורך שלכם. שום דבר לא נכנס או יוצא ממנה בלי שתאפשרו זאת.


ל-VNet מגדירים טווח כתובות (Address Space), למשל 10.0.0.0/16, ואז מחלקים אותו ל-Subnets (תתי-רשת) — ה"חדרים" בתוך הקומה.

📐 חוקים חשובים על VNet

  • VNet שייך לרג'ין אחד בלבד ולא יכול להתפרס על כמה רג'ינים
  • כל Subnet בתוכו הוא תת-קבוצה של הכתובות של ה-VNet, ואינו יכול לחפוף לתת-רשת אחרת
  • מחשבים (VMs) ומשאבים מקבלים כרטיס רשת (NIC) עם כתובת IP מתוך ה-Subnet
  • שתי VNets עם טווחי כתובות חופפים לא יכולות להתחבר זו לזו (Peering) — צריך טווחים שונים

⚠️ טריק שחשוב לדעת: Azure "גונב" 5 כתובות מכל Subnet

בניגוד לרשת ביתית, Azure שומר לעצמו 5 כתובות בכל Subnet לשימוש פנימי (כתובת הרשת, שער ברירת מחדל, שתי כתובות DNS פנימיות, וכתובת ה-Broadcast). לכן ב-Subnet בגודל /24 (256 כתובות) — יש בפועל 251 כתובות זמינות למחשבים שלכם.

🏢 VNet: 10.0.0.0/16 (סה"כ 65,536 כתובות) — West Europe
🚪 Subnet "Frontend": 10.0.1.0/24 — שרתי אתר
🗄️ Subnet "Backend": 10.0.2.0/24 — מסדי נתונים
🔥 Subnet "AzureFirewallSubnet": 10.0.3.0/26 — חומת אש
🔌 Subnet "GatewaySubnet": 10.0.4.0/27 — VPN/ExpressRoute Gateway
# יצירת VNet עם Subnet ראשון:
az network vnet create \
--resource-group MyRG --name MyVNet \
--address-prefix 10.0.0.0/16 \
--subnet-name Frontend --subnet-prefix 10.0.1.0/24

# הוספת Subnet נוסף לאותו VNet:
az network vnet subnet create \
--resource-group MyRG --vnet-name MyVNet \
--name Backend --address-prefix 10.0.2.0/24

💼 דוגמה מהעולם האמיתי

בית חולים בונה VNet אחד לכל הקמפוס, עם Subnet נפרד למכשור רפואי מחובר-רשת (IoT), Subnet נפרד לתחנות העבודה של הצוות, ו-Subnet מבודד לגמרי למאגר רשומות המטופלים הרגיש — כך שגם אם מחשב עובד נדבק בווירוס, הוא לא יכול להגיע ישירות למאגר הרשומות הרפואיות.

// 09 — אבטחת רשת

Network Security Group — ה"מאבטח" של הרשת

מי מותר לו להיכנס ולצאת מכל Subnet או כרטיס רשת.

🛡️ מה זה NSG?

Network Security Group (NSG) היא רשימת חוקים (כמו רשימת המאבטח) שמצמידים ל-Subnet או לכרטיס רשת (NIC) של VM. כל חוק מגדיר: מאיפה, לאן, באיזה פורט, ואיזה פרוטוקול — ואם להתיר (Allow) או לחסום (Deny).


NSG הוא Stateful — אם התרתם בקשה נכנסת, התשובה שלה יוצאת אוטומטית מבלי צורך בחוק נפרד.

🔢 סדר עדיפויות (Priority)

לכל חוק יש מספר Priority בין 100 ל-4096. ככל שהמספר נמוך יותר — הוא נבדק ראשון. ברגע שנמצאה התאמה לחוק, Azure מפסיק לבדוק חוקים נוספים.

שם ברירת מחדלPriorityמה הוא עושה
AllowVNetInBound65000מתיר תעבורה בין משאבים באותו VNet
AllowAzureLoadBalancerInBound65001מתיר בדיקות תקינות מ-Load Balancer
DenyAllInBound65500חוסם כל תעבורה נכנסת אחרת מהאינטרנט — כברירת מחדל!
AllowVNetOutBound / AllowInternetOutBound65000-65001מתיר יציאה חופשית לרשת/לאינטרנט

💡 המסקנה החשובה ביותר

בברירת מחדל, שום דבר לא נכנס ל-Subnet חדש מהאינטרנט — אתם חייבים ליצור חוק Allow מפורש (למשל: "התר RDP רק מכתובת ה-IP הביתית שלי"). לעומת זאת, יציאה החוצה מותרת אוטומטית.

🏷️ Application Security Group (ASG)

במקום לכתוב כללי NSG לכל כתובת IP בנפרד, אפשר לקבץ כמה כרטיסי רשת תחת ASG (למשל "WebServers") ולכתוב חוק אחד שמתייחס לכל הקבוצה. נוח מאוד כשמוסיפים/מסירים שרתים.

🌐 Public IP — Standard SKU בלבד

חשוב לדעת: כתובות IP ציבוריות מסוג Standard הן מאובטחות כברירת מחדל — חסומות לחלוטין עד שתגדירו NSG שמתיר גישה. (מסוג Basic, הישן יותר, יצא משימוש והוחלף לגמרי ב-Standard).

# יצירת NSG וחוק שמתיר RDP רק מכתובת IP ספציפית:
az network nsg create --resource-group MyRG --name MyNSG

az network nsg rule create \
--resource-group MyRG --nsg-name MyNSG \
--name Allow-RDP-FromHome --priority 100 \
--source-address-prefixes 203.0.113.5/32 \
--destination-port-ranges 3389 \
--protocol Tcp --access Allow

💼 דוגמה מהעולם האמיתי

חברת הייטק מגלה בלוגים שכולם בעולם מנסים להתחבר לפורט RDP (3389) של השרתים שלה. היא יוצרת כלל NSG שמתיר RDP רק מכתובת ה-IP הציבורית של משרדי החברה, וחוסמת את כל השאר. בתוך שבוע, ניסיונות ההתחברות הזדוניים מהאינטרנט צונחים לאפס.

// 10 — חיבור בין רשתות

Peering ו-Routing

איך שתי VNets מדברות ביניהן, ואיך שולטים בדיוק לאן התעבורה הולכת.

🔗 VNet Peering

Peering מחבר שתי VNets כך שהמשאבים בהן יכולים לדבר ביניהם באמצעות כתובות IP פרטיות — התעבורה עוברת ברשת הפנימית של מיקרוסופט ולא דרך האינטרנט הציבורי, מהר ומאובטח.


אפשר לחבר VNets גם בין רג'ינים שונים (Global Peering).

⚠️ Peering לא טרנזיטיבי!

אם VNet A מחובר ל-B, ו-B מחובר ל-C — A לא יכול "לעבור דרך" B כדי להגיע ל-C אוטומטית. לצורך חיבורים מורכבים בין הרבה VNets (טופולוגיית Hub-Spoke) נהוג להשתמש ב-Azure Firewall או Virtual WAN שמנתבים תעבורה במרכז.

טופולוגיית Hub-Spoke נפוצה: כל התעבורה בין ה-Spokes וגם החוצה עוברת דרך ה-Hub לבדיקה מרכזית

🗺️ Route Table (UDR — User Defined Route)

Azure כבר יודע לנתב תעבורה אוטומטית (System Routes) — למשל בין Subnets באותו VNet, או לאינטרנט. Route Table מאפשר לדרוס את ברירת המחדל ולהגיד: "כל תעבורה מסוימת — תעבור קודם דרך X".

🔥 שימוש נפוץ: כפיית תעבורה דרך Firewall

החוק הנפוץ ביותר: 0.0.0.0/0 → הכתובת הפרטית של Azure Firewall. כך כל תעבורה יוצאת מה-Subnet (לכל יעד) עוברת קודם דרך חומת האש לבדיקה, במקום לצאת ישירות.

# יצירת Peering בין שני VNets (משני הכיוונים):
az network vnet peering create --name HubToSpokeA \
--resource-group MyRG --vnet-name HubVNet \
--remote-vnet SpokeAVNet --allow-vnet-access

# יצירת Route Table שמפנה הכל דרך ה-Firewall:
az network route-table create --resource-group MyRG --name ToFirewall
az network route-table route create --resource-group MyRG \
--route-table-name ToFirewall --name DefaultToFW \
--address-prefix 0.0.0.0/0 --next-hop-type VirtualAppliance \
--next-hop-ip-address 10.0.3.4

💼 דוגמה מהעולם האמיתי

רשת בתי מלונות עם 30 סניפים (VNet נפרד לכל מלון) מחברת את כולם בטופולוגיית Hub-Spoke ל-VNet מרכזי אחד עם Azure Firewall. כל תעבורה בין מלון למלון, ובין מלון לאינטרנט, עוברת דרך ה-Hub ונבדקת במקום אחד — במקום להגדיר 30 חומות אש נפרדות ולתחזק את כולן.

// 11 — חיבור מחוץ ל-Azure

חיבור On-Prem ↔ Azure

איך מחברים משרד פיזי, בית או מרכז נתונים קיים לרשת שב-Azure.

🌐 Public IP ו-🚪 NAT Gateway

Public IP נותן למשאב כתובת גלויה לאינטרנט (למשל ל-Load Balancer או VM שצריך להיות נגיש מבחוץ).


NAT Gateway פותר בעיה הפוכה: איך VMs פרטיים יוצאים לאינטרנט (לעדכונים, API חיצוני) בלי לתת לכל אחד מהם כתובת ציבורית משלו. ה-NAT Gateway "מלווה" את כל היציאה דרך כתובת ציבורית אחת משותפת, ומונע גם בעיית אזילת פורטים (SNAT exhaustion).

🔐 VPN Gateway

VPN Gateway יוצר מנהרה מוצפנת מעל האינטרנט הציבורי הרגיל, בין הרשת שלכם ל-VNet:

  • Site-to-Site (S2S) — מחבר משרד/מרכז נתונים שלם ל-Azure
  • Point-to-Site (P2S) — מחבר מחשב בודד (עובד מהבית) ישירות ל-VNet
  • VNet-to-VNet — מחבר שני VNets (חלופה ל-Peering, למשל בין ענני Azure שונים)

🚄 ExpressRoute — קו פרטי, לא דרך האינטרנט בכלל

ExpressRoute הוא חיבור פיזי ייעודי בין הרשת שלכם ל-Azure, דרך ספק תקשורת שותף — ללא מעבר כלשהו באינטרנט הציבורי. התוצאה: אמינות גבוהה יותר, השהיה (Latency) נמוכה ויותר יציבה, ורוחב פס גדול. יקר יותר מ-VPN אבל קריטי לארגונים גדולים או לתעבורה רגישה (למשל רפליקציה בין Domain Controllers מקומיים לענן).

עלותנמוכה יחסיתגבוהה יותר

# יצירת NAT Gateway ליציאה לאינטרנט בלי חשיפת VMs:
az network public-ip create --resource-group MyRG --name NatIP --sku Standard

--public-ip-addresses NatIP
az network vnet subnet update --resource-group MyRG --vnet-name MyVNet \
--name Backend --nat-gateway MyNAT

💼 דוגמה מהעולם האמיתי

חברת ביטוח עם משרד ראשי בתל אביב מקימה ExpressRoute כי היא זקוקה לחיבור אמין ומהיר במיוחד לרפליקציית ה-Active Directory שלה מול הענן, 24/7. לעומתה, סניף קטן עם חמישה עובדים מסתפק ב-VPN Gateway רגיל — הרבה יותר זול, ומספיק לצרכים שלו.

איזון עומסים — מי מכוון לאן

⚖️ Load Balancer — "השוטר בצומת"

מפזר חיבורי רשת (TCP/UDP) בין כמה שרתים לפי כללים פשוטים (למשל Round Robin), בלי להסתכל בכלל על תוכן ה-HTTP. מהיר מאוד ומתאים לכל סוג תעבורה.

🚪 Application Gateway — "הפקידה שבודקת את הטופס"

מבין HTTP/HTTPS ויכול לנתב לפי כתובת ה-URL או הדומיין (למשל /api לשרת אחד ו-/images לשרת אחר), ומגיע עם WAF (חומת אש לאפליקציות ווב) מובנה.

🌍 Azure Front Door — הדלת הראשית העולמית

פועל בקצוות הרשת של מיקרוסופט ברחבי העולם (Anycast) — משתמש מתחבר לנקודה הקרובה אליו גיאוגרפית, ומשם מנותב פנימה לרג'ין הקרוב שבו רץ השירות שלכם. כולל גם CDN (Cache לתוכן סטטי) ו-WAF.

📖 Traffic Manager — "מכוון תנועה ברמת ה-DNS בלבד"

לא רואה תעבורה בפועל — הוא רק עונה לשאלת DNS "לאן לפנות" (למשל לפי רג'ין הכי קרוב, או Failover אם רג'ין שלם נופל). שימושי גם לפרוטוקולים שאינם HTTP.

💼 דוגמה מהעולם האמיתי

אתר חדשות גלובלי משתמש ב-Azure Front Door כדי שגולש מיפן יקבל את דף הבית מרג'ין קרוב באסיה תוך מילישניות, בעוד גולש מגרמניה מקבל אותו מרג'ין באירופה — ושניהם רואים תמונות ששמורות כבר ב-CDN הפנימי, במקום שהן ייטענו מחדש מהשרת המקורי בכל פעם.

// 13 — גישה פרטית לשירותים

Private Link ו-Service Endpoints

איך ניגשים לשירותי PaaS (כמו Storage או SQL) בלי לצאת בכלל לאינטרנט הציבורי.

🤔 הבעיה

שירותי PaaS כמו Azure Storage או Azure SQL Database נגישים לרוב דרך כתובת ציבורית (עם אימות, אך עדיין דרך האינטרנט). לפעמים רוצים שהתעבורה מה-VNet לשירות כזה תישאר לגמרי פרטית.

🔒 Private Endpoint

יוצר כרטיס רשת עם כתובת IP פרטית בתוך ה-Subnet שלכם, שמצביע ישירות על שירות ה-PaaS הספציפי. מבחינת שאר ה-VNet, השירות "נראה" כמו עוד משאב פנימי רגיל. אפשר גם לחסום גישה ציבורית לגמרי לשירות.

🛣️ Service Endpoint

פתרון פשוט וישן יותר: מרחיב את "הזהות" של ה-VNet לשירות, כך שהתעבורה נשארת ברשת הפנימית של מיקרוסופט — אבל השירות עדיין עונה על כתובת ציבורית, ולא מקבל כתובת פרטית ייעודית משלו.

חברת פינטק ששומרת נתוני כרטיסי אשראי ב-Azure SQL Database מתחברת אליו רק דרך Private Endpoint, וחוסמת גישה ציבורית לגמרי — כך שגם אם מישהו יגלה את שם השרת, הוא פיזית לא יכול להגיע אליו מהאינטרנט. זו דרישה נפוצה בביקורות תאימות כמו PCI-DSS.

// 14 — פתרון שמות

Azure DNS

איך שמות דומיין מתורגמים לכתובות IP — גם בציבור וגם בתוך הרשת הפרטית.

🌍 Azure DNS (Public Zones)

שירות שמאפשר לארח את רשומות ה-DNS של דומיין ציבורי שלכם (למשל mycompany.com) ישירות ב-Azure — עם ביצועים גבוהים וזמינות עולמית.

🏠 Azure Private DNS Zone

פותר שמות בתוך ה-VNet בלבד — למשל לתת לשרת פנימי שם קריא כמו db01.internal.local במקום לזכור כתובת IP. אפשר לחבר את אותו Private DNS Zone לכמה VNets, וגם הוא חיוני לעבודה נכונה עם Private Endpoint (כדי שהשם הציבורי של השירות "יפנה" לכתובת הפרטית).

💡 חיבור בין הנושאים

זוכרים את "ספר הטלפונים" מיסודות הרשת? זה בדיוק מה ש-DNS עושה גם כאן — רק שעכשיו יש לנו שני "ספרים": אחד לעולם החיצון (Public Zone) ואחד פנימי לרשת הפרטית שלכם (Private Zone).

💼 דוגמה מהעולם האמיתי

אתר איקומרס קונה דומיין (shop.com) ומנהל אותו ב-Azure DNS הציבורי, בעוד שבתוך ה-VNet הפנימי שלו Private DNS Zone מאפשר לשרתים לקרוא זה לזה בשמות פשוטים כמו db-primary.internal — במקום לזכור כתובות IP שמשתנות מדי פעם.

// 15 — הגנה מתקדמת

Azure Firewall, WAF ו-DDoS

כשה-NSG הפשוט לא מספיק — כלי האבטחה המתקדמים יותר של Azure.

🔥 Azure Firewall

חומת אש מנוהלת (לא צריך לתחזק שרת בעצמכם), ברמת רשת ואפליקציה, ממוקמת בדרך כלל ב-Hub של טופולוגיית Hub-Spoke. יודעת לסנן גם לפי שם דומיין (FQDN) ולא רק IP — למשל "התר גישה רק ל-*.windowsupdate.com".

🌐 WAF — Web Application Firewall

מגן ספציפית על אפליקציות ווב מפני התקפות ברמת האפליקציה — כמו SQL Injection או XSS — על בסיס כללים סטנדרטיים (OWASP). מתחבר ל-Application Gateway או ל-Front Door.

🛡️ DDoS Protection

Basic — פעיל אוטומטית וללא עלות על כל משאב ב-Azure, מגן מפני התקפות נפוצות ברמת התשתית.
Standard — בתשלום, עם מדיניות מותאמת למשאבים שלכם, ניטור מפורט, דוחות התקפה, ואף הגנה כספית (Cost Protection) אם התקפה גורמת ל-Scale-out יקר.

🎁 בונוס: איך מאתרים בדיוק איפה תעבורה נחסמה?

Network Watcher הוא כלי אבחון וניטור לרשת — במקום לנחש למה חבילת מידע לא הגיעה ליעד, אפשר להשתמש בו כדי לבדוק בדיוק איפה בדרך (איזה NSG, איזה Route) היא נעצרה. שימושי מאוד כשמנסים להבין למה משהו "לא עובד" ברשת מורכבת עם הרבה שכבות אבטחה.

💼 דוגמה מהעולם האמיתי

רשת בתי קפה שהאתר שלה נפגע פעמיים בהתקפות SQL Injection מציבה WAF מול Application Gateway — מאותו רגע, ניסיונות ההזרקה נחסמים אוטומטית לפני שהם מגיעים לשרת בכלל, בלי לשנות שורת קוד אחת באתר.

// 16 — תרגול

מעבדה — Hands-On

שישה תרגילים הדרגתיים, מהבסיס ועד טופולוגיה ארגונית מלאה.

1
יצירת VNet עם שני Subnets
קל
  • בפורטל: Create a resource → Virtual Network
  • תנו שם, בחרו Region, והגדירו Address space כ-10.0.0.0/16
  • הוסיפו Subnet בשם "web" בטווח 10.0.1.0/24
  • הוסיפו Subnet שני בשם "data" בטווח 10.0.2.0/24
  • צרו, ובדקו את התוצאה תחת "Diagram" בעמוד ה-VNet
2
NSG שחוסם RDP מכולם חוץ מכם
קל
  • בדקו מה כתובת ה-IP הציבורית שלכם (חיפוש "what is my ip")
  • צרו NSG חדש וצרפו אותו ל-Subnet "web"
  • הוסיפו חוק Inbound: Allow, פורט 3389, מקור = כתובת ה-IP שלכם בלבד, Priority 100
  • ודאו ש-DenyAllInBound (65500) עדיין קיים ולא נמחק
  • נסו לגשת מ-IP אחר (למשל דרך VPN) וודאו שנחסם
3
Peering בין שתי VNets ובדיקת קישוריות
בינוני
  • צרו VNet שני עם טווח שאינו חופף (למשל 10.1.0.0/16)
  • הגדירו Peering בשני הכיוונים בין ה-VNets
  • פרסו VM קטן בכל VNet (בלי Public IP)
  • התחברו ל-VM הראשון (למשל דרך Azure Bastion) ונסו לפנות ל-IP הפרטי של השני
  • ודאו שהתקשורת עוברת — סימן ש-Peering תקין
4
יציאה לאינטרנט בלי Public IP — NAT Gateway
בינוני
  • פרסו VM ללא Public IP כלל בתוך Subnet קיים
  • צרו Public IP חדש מסוג Standard
  • צרו NAT Gateway וחברו אליו את ה-Public IP
  • שייכו את ה-NAT Gateway ל-Subnet של ה-VM
  • מתוך ה-VM, בצעו בקשת יציאה (למשל curl לאתר בדיקת IP) וודאו שמוצג ה-IP של ה-NAT
5
טופולוגיית Hub-Spoke עם Azure Firewall
מתקדם
  • צרו Hub VNet עם Subnet מיוחד בשם המדויק "AzureFirewallSubnet" (לפחות /26)
  • פרסו בו Azure Firewall וקבלו את ה-IP הפרטי שלו
  • צרו שני Spoke VNets, כל אחד Peering אל ה-Hub
  • צרו Route Table בכל Spoke עם חוק 0.0.0.0/0 → IP הפרטי של ה-Firewall, וצרפו ל-Subnets
  • הגדירו כלל ב-Firewall שמתיר תעבורה בין ה-Spokes, ובדקו בלוגים שהיא אכן עוברת דרכו
6
Private Endpoint לחשבון אחסון וחסימת גישה ציבורית
מתקדם
  • צרו Storage Account ונטרלו בו "Public network access"
  • צרו Private Endpoint בתוך ה-VNet, מקושר ל-Storage Account (Sub-resource: blob)
  • אשרו את החיבור (אם לא אושר אוטומטית) וצרו Private DNS Zone בשם privatelink.blob.core.windows.net
  • קשרו את ה-Private DNS Zone ל-VNet שלכם
  • מתוך VM בתוך ה-VNet, בדקו ששם ה-Storage Account פונה לכתובת פרטית — ושגישה מבחוץ נחסמת

מילון Azure Networking

כל המונחים המופיעים באתר, עם הסבר רחב לכל אחד — בדיוק כמו שרואים בהעברת עכבר מעל מונח בתוך שיעור.

AKS
Azure Kubernetes Service — שירות שמריץ עבורכם תוכנה בשם Kubernetes, שמנהלת אוטומטית הרבה 'קופסאות' קטנות של קוד (מכולות/Containers) בלי שתצטרכו לנהל את השרתים שמתחתיהן בעצמכם.
Anycast
טכניקת רשת שבה אותה כתובת מפורסמת מכמה מקומות בעולם בו-זמנית, וכל משתמש 'נתפס' אוטומטית על ידי המיקום הקרוב אליו גיאוגרפית.
Application Gateway
כמו Load Balancer, אבל 'חכם' יותר — הוא כן מבין את תוכן הבקשה (HTTP), ויכול להחליט לאיזה שרת לשלוח אותה לפי הכתובת המדויקת שהמשתמש ביקש. כולל גם הגנה מובנית (WAF).
Archive
דרגת האחסון הזולה ביותר ב-Blob Storage, מתאימה לקבצים שכמעט אף פעם לא נוגעים בהם — אבל אם צריך לשלוף קובץ משם, זה יכול לקחת שעות במקום שניות.
ARM
Azure Resource Manager — המנוע הפנימי שמבצע בפועל כל פעולת ניהול ב-Azure, גם אם ביקשתם אותה דרך הפורטל, ה-CLI או ה-PowerShell.
ARM Template / Bicep
קובץ טקסט שמתאר איך אמורה להיראות התשתית שלכם (אילו משאבים, עם אילו הגדרות), כדי שתוכלו ליצור אותה שוב ושוב בלחיצת כפתור בצורה זהה בכל פעם.
ASG
Application Security Group — דרך לקבץ יחד כמה שרתים תחת שם אחד (למשל 'שרתי אתר'), כדי לכתוב חוק אבטחה אחד לכולם במקום חוק נפרד לכל שרת.
Availability Zone
מיקום פיזי נפרד לגמרי בתוך אותו Region, עם חשמל, קירור וחיבור רשת עצמאיים משלו — כדי שאם מרכז נתונים אחד נופל, האחרים ימשיכו לעבוד.
Azure Advisor
כלי שסורק את הסביבה שלכם ונותן המלצות אישיות לשיפור — למשל 'שרת הזה בקושי בשימוש, אפשר להקטין אותו ולחסוך כסף'.
Azure App Service
שירות שמריץ עבורכם אתר או API, כשאתם רק מעלים את הקוד — Azure דואג לשרת, לגיבוי ולהתאמת קנה המידה מאחורי הקלעים.
Azure Backup
שירות מנוהל לגיבוי אוטומטי ומתוזמן של שרתים, מסדי נתונים וקבצים, כך שאפשר לשחזר אותם אם קורה נזק או טעות.
Azure Batch
שירות שמריץ עבודות חישוב כבדות על הרבה מחשבים במקביל בו-זמנית — למשל עיבוד וידאו ארוך שמתחלק לחלקים קטנים שרצים יחד.
Azure Blueprints
שירות ישן שריכז יחד תבניות, פוליסות והרשאות לפריסת סביבות אחידות. מיקרוסופט הוציאה אותו משימוש, וממליצה כיום על Template Specs ו-Deployment Stacks במקומו.
Azure CLI
כלי שורת פקודה (טקסט, לא גרפי) לניהול Azure, שמאפשר לכתוב סקריפטים ולחזור בדיוק על אותה פעולה פעמים רבות בקלות.
Azure Data Factory
שירות לתזמון והעברת נתונים בין מערכות שונות (תהליך שנקרא ETL) — כמו פס ייצור שאוסף חומרי גלם (נתונים) ממקומות שונים ומעביר אותם למקום מרכזי אחד מעובד.
Azure DevOps
פלטפורמה של מיקרוסופט לניהול כל מחזור החיים של פיתוח תוכנה במקום אחד: שמירת קוד (Repos), ניהול משימות (Boards), אוטומציה של בנייה ופריסה (Pipelines), ואחסון חבילות (Artifacts).
Azure DNS
השירות שמארח את רשומות ה-DNS הציבוריות שלכם — 'ספר הטלפונים' שהופך שם כמו mysite.com לכתובת IP שהאינטרנט יודע להשתמש בה.
Azure Files
שיתוף קבצים מנוהל בענן, שנראה למחשב כמו כונן רשת רגיל — נוח להחלפת שרת קבצים ישן במשרד.
Azure Firewall
שירות חומת אש מנוהל שממוקם בדרך כלל במרכז הרשת של הארגון, ובודק ומסנן תעבורה בין אזורים שונים — כולל יכולת לחסום גישה לפי שם אתר (FQDN) ולא רק לפי כתובת IP.
Azure Functions
שירות שמריץ קטע קוד קטן רק כשקורה משהו שמפעיל אותו (כמו בקשת אינטרנט או קובץ חדש), ומחייב אתכם רק על השניות שבהן הקוד באמת רץ.
Azure Key Vault
כספת דיגיטלית מרכזית לאחסון בטוח של סודות (כמו סיסמאות), מפתחות הצפנה ותעודות דיגיטליות — כדי שהם לא יישמרו בטעות בתוך קוד המקור של האפליקציה.
Azure Logic Apps
כלי שמאפשר לבנות תהליכים אוטומטיים בין הרבה שירותים שונים (כמו 'כשמגיע מייל חדש, שמור את הקובץ המצורף ב-Storage') כמעט בלי לכתוב קוד בכלל.
Azure Machine Learning
שירות לבניית, אימון ופריסת מודלים של למידת מכונה — תוכניות שלומדות דפוסים מנתוני עבר כדי לחזות או לסווג מידע חדש.
Azure Monitor
שירות שאוסף ומציג מדדי ביצועים ולוגים מכל המשאבים שלכם ב-Azure, כדי שתוכלו לדעת מה קורה בפועל ולקבל התראה כשמשהו משתבש.
Azure Pipelines
הרכיב באזור-דבאופס שמריץ בפועל את תהליך ה-CI/CD — לוקח קוד חדש, בונה אותו, בודק אותו, ומפרסם אותו, לפי קובץ הגדרות בפורמט YAML.
Azure Policy
מנגנון שאוכף חוקים על כל מה שנוצר ב-Azure — למשל 'אסור ליצור משאבים מחוץ לישראל'. יכול רק להתריע (Audit) או גם לחסום בפועל (Deny).
Azure Portal
האתר הגרפי הרשמי לניהול Azure — לוחות בקרה, אשפים ליצירת משאבים, וגרפים לניטור. הכי נוח למי שרק מתחיל.
Azure PowerShell
כלי דומה מאוד ל-Azure CLI, אבל מבוסס על שפת הסקריפטים PowerShell של מיקרוסופט — נוח במיוחד למי שכבר מכיר אותה.
Azure SQL Database
מסד נתונים יחסי מנוהל, מבוסס על אותה טכנולוגיה כמו SQL Server — טבלאות, קשרים ביניהן, ושפת שאילתות SQL רגילה — בלי שתצטרכו לתחזק שרת בעצמכם.
Azure Storage Account
ה'מיכל' העל שבתוכו חיים שירותי האחסון של Azure: קבצים (Blob), שיתופי קבצים (Files), תורים (Queues) וטבלאות (Tables).
Azure Synapse Analytics
פלטפורמת ענק לניתוח כמויות אדירות של מידע (Big Data), שמשלבת מנועי שאילתה שונים (כולל SQL ו-Spark) במקום אחד.
Azure Virtual Machine
שרת וירטואלי מלא בענן, שנותן לכם שליטה מלאה על מערכת ההפעלה — בדיוק כמו שרת פיזי, רק שהוא רץ בתוך מחשב ענק של מיקרוסופט.
Big Data
כינוי לכמויות מידע כל כך גדולות ומגוונות, שכלים ומסדי נתונים 'רגילים' כבר לא מספיקים כדי לעבד אותן ביעילות.
Blob Storage
שירות לאחסון קבצים 'גולמיים' בכמויות עצומות — תמונות, סרטונים, גיבויים — עם דרגות מחיר שונות לפי כמה פעמים ניגשים לקובץ.
CDN
Content Delivery Network — רשת של שרתים ברחבי העולם ששומרים עותק (מטמון) של תוכן קבוע כמו תמונות, כדי שמשתמשים יקבלו אותו מהר מהמיקום הכי קרוב אליהם, ולא מהשרת המקורי הרחוק.
CI/CD
Continuous Integration / Continuous Delivery — תהליך אוטומטי שבודק כל שינוי קוד חדש מיד (CI), ומכין אותו (או אף מפרסם אותו) אוטומטית לסביבת הייצור (CD), במקום לחכות לעדכון גדול ונדיר.
CIDR
צורת כתיבה כמו 10.0.0.0/24 שאומרת כמה כתובות רשת יש בקבוצה מסוימת. ככל שהמספר אחרי הקו הנטוי (ה'/') קטן יותר, כך יש יותר כתובות בקבוצה.
Conditional Access
מנגנון שמחליט בזמן אמת, מעבר לסיסמה נכונה, אם להתיר כניסה — לפי מיקום, סוג המכשיר, ורמת החשד שההתחברות הזו מסוכנת.
Container
'קופסה' קלה שמכילה בתוכה אפליקציה וכל מה שהיא צריכה כדי לרוץ, כך שהיא תתנהג אותו הדבר בכל מחשב שמריץ אותה — בלי הפתעות של 'זה עבד רק אצלי'.
Cosmos DB
מסד נתונים מסוג NoSQL (לא מבוסס טבלאות קשיחות) שבנוי מלכתחילה לפיזור גלובלי — אפשר לשכפל את הנתונים לעשרות מדינות כדי שכל משתמש בעולם יקבל תשובה מהירה.
Cost Management
כלים מובנים ב-Azure למעקב אחרי ההוצאה החודשית, הגדרת תקציבים והתראות כשההוצאה חורגת מהצפוי.
Data Center
מרכז נתונים — מבנה פיזי ענק מלא בשרתים, מערכות קירור וגיבויי חשמל, שבו יושבים המחשבים שמריצים בפועל את שירותי הענן.
DDoS Protection
הגנה מפני התקפות שמטרתן להציף שירות בכמות עצומה של בקשות מזויפות, כדי להפיל אותו ולמנוע משתמשים אמיתיים לגשת אליו.
DevOps
גישת עבודה שמאחדת בין צוותי הפיתוח (Dev) לצוותי התפעול (Ops), כדי לשחרר עדכונים לתוכנה מהר יותר, בתדירות גבוהה יותר, ועם פחות תקלות.
Entra Domain Services
לשעבר Azure AD DS — שירות מנוהל שנותן יכולות מוכרות של Active Directory (כמו Kerberos ו-LDAP), בלי שתצטרכו להקים ולתחזק Domain Controllers משלכם בענן.
Entra External ID
לשעבר Azure AD B2C — שירות לניהול זהויות של לקוחות חיצוניים לאתר או לאפליקציה (לא עובדים פנימיים), כולל התחברות עם Google או Facebook.
ETL
Extract, Transform, Load — שלושה שלבים: לשלוף נתונים ממקור, לעבד/לנקות אותם, ולהכניס אותם למקום היעד — כך שאפשר יהיה לנתח אותם בקלות אחר כך.
ExpressRoute
קו תקשורת פרטי וייעודי בין הרשת שלכם ל-Azure, שעובר דרך ספק תקשורת ולא דרך האינטרנט הציבורי בכלל — יציב ומהיר יותר מ-VPN רגיל, אך גם יקר יותר.
Front Door
שירות שמהווה את 'שער הכניסה' העולמי לאתר או לאפליקציה שלכם — הוא מפנה כל משתמש לרג'ין הקרוב אליו גיאוגרפית, ומגיע גם עם מטמון (CDN) והגנה (WAF).
GitHub Actions
מנגנון אוטומציה שמוטמע ישירות בתוך מאגר קוד ב-GitHub, ומאפשר להריץ בדיקות ופריסות (כולל ל-Azure) אוטומטית בכל שינוי קוד — בלי צורך בכלי חיצוני נפרד.
HPC
High Performance Computing — חישוב בעוצמה גבוהה מאוד, בדרך כלל על ידי חלוקת עבודה אחת גדולה להרבה מחשבים שעובדים עליה יחד במקביל.
Hub-Spoke
צורת ארגון רשת שבה כמה VNets 'לוויין' (Spokes) מתחברים כולם ל-VNet מרכזי אחד (Hub), שדרכו עוברת כל תעבורת האבטחה והניתוב המרכזי.
Hybrid Cloud
שילוב בין תשתית On-Premises פרטית לבין ענן ציבורי, המחוברות זו לזו (למשל דרך VPN Gateway או ExpressRoute) ועובדות יחד כמערכת אחת.
IaaS
Infrastructure as a Service — אתם מקבלים חומרה בסיסית בענן (שרת, רשת) ואחראים בעצמכם על כל מה שמעליה, כולל מערכת ההפעלה.
Kerberos
פרוטוקול אימות ותיק ונפוץ ברשתות ארגוניות, שמאפשר למחשב להוכיח מי הוא בלי לשלוח את הסיסמה עצמה ברשת בכל פעם — במקום זאת נעשה שימוש ב'כרטיסים' זמניים.
Kubernetes
תוכנה שמנהלת אוטומטית הרבה Containers ביחד — מדליקה אותם, מכבה אותם, ומחליפה אותם אם הם קורסים, כמעט בלי מעורבות אנושית.
LDAP
פרוטוקול שמשמש לחיפוש ולקריאה מתוך 'ספרייה' של משתמשים וקבוצות (למשל Active Directory) — כמו שפה משותפת שאפליקציות שונות משתמשות בה כדי לשאול 'מי המשתמש הזה ומה מותר לו'.
Load Balancer
שירות שמפזר תעבורת רשת (כמו בקשות מגולשים) בין כמה שרתים זהים, כדי שאף שרת אחד לא יעמוס יותר מדי. הוא לא 'קורא' את תוכן הבקשה, רק מפנה אותה הלאה.
Log Analytics
מאגר מרכזי שאליו נשלחים לוגים ומדדים מכל הסביבה, כדי שאפשר יהיה לחפש ולנתח אותם במקום אחד — הבסיס שעליו בנויים גם Azure Monitor וגם Microsoft Sentinel.
Machine Learning
תחום שבו תוכנה 'לומדת' דפוסים מתוך דוגמאות רבות של מידע (במקום שמתכנת יכתוב חוק ידני לכל מקרה), כדי לקבל החלטות או תחזיות על מידע חדש שהיא לא ראתה קודם.
Management Group
שכבת ניהול שיושבת מעל כמה Subscriptions יחד, כדי לאכוף באחת מדיניות אחידה (כמו הרשאות או Azure Policy) על כל הארגון.
MFA
Multi-Factor Authentication — אימות דו-שלבי: מעבר לסיסמה, נדרש גם אמצעי נוסף (כמו קוד שמגיע לנייד), כדי שגם אם הסיסמה נגנבה, התוקף עדיין לא יוכל להיכנס.
Microsoft Defender for Cloud
פלטפורמת אבטחה שסורקת את כל הסביבה שלכם ונותנת ציון ('Secure Score') שמראה כמה אתם חשופים, יחד עם המלצות קונקרטיות לתיקון.
Microsoft Entra ID
השם הנוכחי של השירות שהיה נקרא Azure Active Directory — שירות ניהול הזהויות המרכזי של הארגון: מי המשתמשים, מה ההרשאות שלהם, ואיך הם מתחברים בבטחה.
Microsoft Sentinel
כלי מבוסס ענן שאוסף לוגים והתראות מכל הסביבה שלכם, מזהה דפוסים חשודים בעזרת ניתוח חכם, ויכול אף להפעיל תגובה אוטומטית — כמו 'חדר בקרה' מרכזי לאבטחה.
NAT Gateway
רכיב שנותן למחשבים בתוך VNet לצאת לאינטרנט (למשל להוריד עדכונים) דרך כתובת ציבורית משותפת, בלי שכל מחשב יצטרך כתובת ציבורית משלו.
Network Watcher
כלי ניטור ואבחון לרשת — מאפשר, למשל, לבדוק בדיוק למה חבילת מידע נחסמה בדרך בין שני שרתים.
NoSQL
משפחת מסדי נתונים שלא חייבים סכמה (מבנה טבלאות) קבועה מראש, וגמישים יותר למידע לא אחיד — לרוב על חשבון חלק מהיכולות של מסד נתונים יחסי קלאסי.
NSG
Network Security Group — רשימת חוקים שמחליטה מי מותר לו להיכנס או לצאת מ-Subnet או משרת מסוים. אפשר לחשוב עליו כמו מאבטח עם רשימת שמות בכניסה לבניין: אם אתה לא ברשימה, אתה לא נכנס.
NTLM
פרוטוקול אימות ישן יותר מ-Kerberos, עדיין נתמך לצורך תאימות לאחור, אך נחשב פחות מאובטח ומיקרוסופט ממליצה להימנע ממנו כשאפשר.
On-Premises
תשתית שיושבת פיזית 'אצלכם בבית' — שרתים שהארגון קנה, מחזיק ומתחזק בעצמו במקום להשתמש בענן.
OWASP
ארגון שמפרסם רשימה מוכרת של סוגי ההתקפות הנפוצות ביותר על אתרים ואפליקציות ווב (כמו SQL Injection), ומשמש בסיס לכללים שכלי הגנה כמו WAF פועלים לפיהם.
P2S
Point-to-Site — סוג חיבור VPN שמחבר מחשב בודד (למשל לפטופ של עובד מהבית) ישירות לרשת הארגונית ב-Azure, בלי לחבר רשת שלמה.
PaaS
Platform as a Service — אתם מקבלים פלטפורמה מוכנה להרצת האפליקציה שלכם, והספק דואג לתחזוקת השרת, העדכונים וקנה המידה.
Peering
חיבור פרטי בין שני VNets, כך שהם יכולים לדבר ביניהם ישירות דרך הרשת הפנימית של מיקרוסופט, בלי לצאת לאינטרנט הציבורי בכלל.
Private Cloud
תשתית ענן שמיועדת לארגון בודד בלבד, ולא משותפת עם אף אחד אחר — יכולה לשבת פיזית אצל הארגון עצמו או אצל ספק שמייעד אותה בלעדית עבורו.
Private DNS Zone
כמו Azure DNS, אבל לשימוש פנימי בלבד בתוך ה-VNet — מאפשר לתת שמות פשוטים למשאבים פנימיים בלי לצאת בכלל לאינטרנט.
Private Endpoint
כתובת רשת פרטית שנותנים לשירות ענן (כמו מסד נתונים) כדי שהוא 'ייכנס' פיזית לתוך ה-VNet שלכם, ואפשר יהיה לחסום אליו לגמרי גישה מהאינטרנט הציבורי.
Private IP
כתובת רשת פנימית שמשמשת רק בתוך אותה רשת פרטית — כמו מספר דירה בתוך בניין, שלא ניתן להגיע אליו ישירות מהרחוב.
Public Cloud
תשתית ענן משותפת שבבעלות ספק כמו מיקרוסופט, אמזון או גוגל, שמשרתת הרבה לקוחות שונים על אותה תשתית פיזית (אך כל אחד מבודד לחלוטין מהאחרים).
Public IP
כתובת רשת שגלויה לכל האינטרנט — כמו כתובת הרחוב של בניין, שכל אחד יכול להשתמש בה כדי להגיע אליכם מבחוץ.
Region
אזור גיאוגרפי (למשל West Europe, שבהולנד) שבו יושבים מרכזי הנתונים הפיזיים של מיקרוסופט. כשיוצרים משאב ב-Azure, בוחרים באיזה אזור הוא 'יגור'.
Region Pair
שני אזורים גיאוגרפיים (Regions) שמיקרוסופט זיווגה יחד, בדרך כלל במרחק בטוח זה מזה, לצורך גיבוי ותכנון להתאוששות מאסון.
Rehydration
התהליך שבו קובץ שנשמר בדרגת האחסון הזולה ביותר (Archive) 'מוחזר לחיים' ונהיה נגיש שוב — תהליך שיכול לקחת שעות.
Resource Group
'תיקייה' לוגית שבה שמים משאבים ששייכים יחד (למשל כל מה שקשור לאתר אחד). מחיקת ה-Resource Group מוחקת את כל מה שבתוכו.
Route Table
אוסף של חוקי ניתוב (UDR) שמוצמד ל-Subnet, וקובע באיזה מסלול תעבורה שיוצאת ממנו תלך.
S2S
Site-to-Site — סוג חיבור VPN שמחבר רשת שלמה (למשל משרד) לרשת אחרת שלמה (VNet ב-Azure), כך שכל המחשבים בשני הצדדים יכולים לדבר זה עם זה.
SaaS
Software as a Service — אתם פשוט משתמשים באפליקציה מוכנה דרך הדפדפן (כמו Outlook Online), בלי לדעת או להתעסק בכלל עם מה שרץ מאחוריה.
Serverless
גישה שבה אתם כותבים רק את הקוד עצמו, ובכלל לא צריכים לחשוב על השרת שמריץ אותו — הענן דואג לכל התשתית מאחורי הקלעים.
Service Endpoint
דרך ישנה יותר לתת לשירות ענן 'להכיר' את ה-VNet שלכם, כדי שהתעבורה תישאר ברשת הפנימית של מיקרוסופט — אך בלי לתת לשירות כתובת פרטית משלו כמו ב-Private Endpoint.
Site Recovery
שירות שמשכפל שרתים שלמים לרג'ין אחר, כך שאם רג'ין שלם נופל (למשל בגלל אסון), אפשר 'להפעיל' את העותק במקום אחר תוך דקות.
SMB/NFS
שני פרוטוקולים נפוצים לשיתוף קבצים ברשת — SMB נפוץ בעולם Windows, NFS נפוץ בעולם Linux.
SNAT
Source NAT — התהליך הטכני של 'תרגום' הכתובת הפרטית של מחשב לכתובת ציבורית, ברגע שהתעבורה שלו יוצאת מהרשת הפנימית אל האינטרנט.
Spark
מנוע עיבוד נתונים מהיר שיודע לפצל עבודה גדולה על הרבה מחשבים במקביל, נפוץ מאוד לניתוח Big Data.
SQL Injection
התקפה שבה תוקף מזריק פקודות מסד-נתונים זדוניות דרך שדה קלט רגיל באתר (כמו תיבת חיפוש), בניסיון לגנוב או לשנות מידע.
SSO
Single Sign-On — התחברות פעם אחת שממשיכה לעבוד אוטומטית בכל שאר האפליקציות המחוברות, בלי צורך להקליד סיסמה מחדש בכל אחת מהן בנפרד.
Subnet
תת-רשת — חלוקה פנימית של ה-VNet לאזורים קטנים יותר, כמו חלוקת הקומה לחדרים נפרדים. כל שרת או משאב מקבל כתובת מתוך אחד מה-Subnets האלה.
Subscription
יחידת חיוב וניהול הרשאות ב-Azure. לכל Subscription יש הרשאות משלו, וארגון יכול להחזיק כמה Subscriptions (למשל אחד לפיתוח ואחד לייצור).
Tenant
גבול הזהות של הארגון כולו ב-Microsoft Entra ID — כמו 'תעודת הזהות הדיגיטלית' של החברה, שמכילה בתוכה את כל המשתמשים וההרשאות שלה, ובתוכה יכולים לחיות כמה Subscriptions.
Traffic Manager
שירות שרק עונה לשאלת ה-DNS 'לאיזו כתובת לפנות' (למשל לפי המדינה של המשתמש), ולא נמצא בפועל בנתיב שבו עוברת התעבורה עצמה.
UDR
User Defined Route — חוק ניתוב שאתם כותבים בעצמכם כדי לשנות את המסלול שבו התעבורה עוברת, במקום להסתמך על ברירת המחדל של Azure.
Virtual WAN
שירות שמנהל אוטומטית קישוריות בין הרבה VNets וסניפים ברחבי העולם, בלי שתצטרכו להגדיר ידנית כל חיבור וכל חוק ניתוב בנפרד.
VMSS
Virtual Machine Scale Set — קבוצת שרתים וירטואליים זהים שגדלה או מצטמצמת אוטומטית לפי כמות התנועה, כדי לחסוך כסף כשאין עומס ולתת מענה כשיש.
VNet
Virtual Network — הרשת הפרטית והמבודדת שאתם בונים בתוך Azure. תחשבו עליה כמו קומה שלמה שאתם שוכרים בבניין משרדים ומחלקים כרצונכם — שום דבר לא נכנס או יוצא ממנה בלי שתאפשרו זאת במפורש.
VPN Gateway
רכיב שמקים 'מנהרה' מוצפנת מעל האינטרנט הציבורי הרגיל, כדי לחבר בבטחה בין הרשת שלכם מחוץ ל-Azure לבין ה-VNet שבתוך Azure.
WAF
Web Application Firewall — שכבת הגנה שמתמקדת ספציפית בהתקפות נגד אתרים ואפליקציות ווב, כמו ניסיון להזריק קוד זדוני לתוך טופס באתר.
XSS
Cross-Site Scripting — התקפה שבה תוקף מצליח להריץ קוד זדוני בדפדפן של משתמש אחר, לרוב על ידי הזרקת קוד לתוך תוכן שהאתר מציג בחזרה למשתמשים.
YAML
פורמט טקסט פשוט לכתיבת קבצי הגדרות (כמו רשימת שלבים לביצוע), נפוץ מאוד לתיאור תהליכי CI/CD.
